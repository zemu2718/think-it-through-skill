# 想清楚 v0.4.0 产品架构说明

> 状态：v0.4.0 当前稳定源码的非规范性架构说明。正式行为、安全和验收合同以 [`REQUIREMENTS.md`](../REQUIREMENTS.md) 为准。
>
> 发布边界：v0.4.0 是当前稳定源码、正式产品合同和最新真实公开发布；同名 Git tag、GitHub Release、可下载 asset 与校验和共同建立公开发布身份，但不提升任何未运行的 runtime 兼容层级。

## 为什么需要 v0.4.0

过去的决策流程可能正确识别“该先验证”，却仍过早接受“做产品、加功能、建设平台或必须自研”这类实现形态。之后的分析会围绕既定形态优化，按实现术语寻找同形竞品，并把没有发现、无法访问或尚未试用误写成“现实中没有替代”。

v0.4.0 增加的是投入前的举证纪律：先用用户要获得的结果定义问题，分开判断问题是否存在、是否足够强、候选方案是否适配，以及现实中是否已有更轻或不同形态的替代。证据不足时，允许的承诺必须更小、更可撤回。

## 为什么不新增 Veto Gate 或协议状态

项目可行性不是一次独立检查，而是横跨现有流程的判断责任：

- R-align 把实现形态降级为候选解法，并澄清用户结果、任务、失败与约束；
- R-method 只选择有增量的认知视角，不把市场调研、build-vs-buy 或反方 Agent 包装成方法卡；
- A 仍只问一个最可能改变方向或投入程度的问题；
- Gate-routing 在用户回答 A 后，才判断是否需要外部事实或独立参与；
- Evidence Gate 负责有界发现、核验与试用证据；
- Participation Gate 只在独立反方有明确增量且获得授权时出现；
- B 根据证据链给出方向、当前承诺上限、no-go 条件和复查触发器。

因此唯一运行时状态机保持不变：

```text
空状态
→ R-align
→ R-method
→ A
→ Gate-routing
→（必要且获授权时）Evidence Gate / Participation Gate
→ B
→ 反馈 / 结束 / 新一轮 R
```

项目可行性也不是第八张方法卡、第五类授权、试用专用 receipt、第五个 core schema 或 DecisionRecord 的项目专用状态。增加这些平行结构会复制现有职责，并让关键保护变成可绕过的可选步骤。

## 四个价值维度与四种认识状态

项目可行性分别判断：

1. 问题存在；
2. 问题强度；
3. 方案适配；
4. 替代生态。

这四个价值维度与事实、推断、假设、未知是正交轴。每个价值维度都可能同时包含不同认识状态；问题存在不能替代问题强度，用户认可概念不能替代方案适配，按实现术语没有搜到也不能替代替代生态核验。

## 两遍搜索而不是一次关键词扫描

只有外部事实会改变路径排序、是否继续或投入边界，且用户已经给出具体 `capability_call` 授权时，才进入 Evidence Gate。

搜索按两遍组织：

1. **用户结果与问题优先**：按目标结果、真实任务、痛点、失败机制和约束寻找路径，降低被当前实现形态锚定的概率；
2. **方案与实现补查**：再按产品类别、行业术语、平台、技术实现和已发现候选扩展核验，补足同形与专业命名结果。

候选空间不是固定厂商清单。它按当前决定动态考虑维持现状、人工或流程调整、直接竞品、相邻类别、非同形产品或服务、平台原生能力、活跃开源或商业项目、工具组合、插件或脚本、薄集成、局部补充和独立自研。不适用可以成立，但必须说明理由；没有发现仍是未知。

## 候选发现、现实核验与试用分层

公开介绍只用于建立候选池，不能证明某个候选真的适合。核验内容随候选类型变化，可以包括 Release、CHANGELOG、Roadmap、活跃分支、近期提交、Issue、PR、许可证或价格、部署、数据权限、迁移和集成边界。

重大投入前，优先用同一组真实任务和成功标准试用最强现实替代。试用记录区分 receipt 支持的执行、用户具体报告的既有执行，以及尚未执行并说明原因。搜索授权不自动授权安装、执行、账号认证、私有数据访问或外部行动。

试用不是为了证明某个候选完美，而是回答更窄的问题：它是否已经解决用户在意的核心任务，是否只需要薄集成或局部补充，以及独立自研还剩下什么经过现实检验的必要性。

## 独立反方为什么是条件能力

默认仍是单 Agent。额外 Agent 只有在任务不重复、可验证、可停止，且认知独立能改变判断时才有增量。此时 Participation Gate 先说明任务、数量、最小上下文、成本和失败降级，再取得独立 `participation_delegation` 授权。

反方不接收主 Agent 的最终判断、偏好方案或完整对话，只接收回答任务所需的最小材料。联网、私有数据和外部行动继续分别授权。主 Agent 负责去重来源、呈现冲突并综合，不按投票决定。

反方未执行、被拒绝或失败时，结果是保留未知并收紧承诺，不是为当前倾向背书。

## 承诺上限

B 可以给出采用、组合或薄集成、有限验证、自研、暂停或停止等方向，但承诺必须与证据链匹配：

- 问题不存在或强度不足时，不继续投入；
- 任一决定敏感价值维度仍未知或冲突，搜索、核验、试用或必要反方存在缺口时，最多做低成本、可撤回的有限验证；
- 最强现实替代已解决全部或部分核心任务时，优先采用、组合或薄集成；
- 只有四个价值维度均有支持、两遍搜索与候选核验完整、最强替代经同任务试用仍不能解决核心问题，且必要反方已经完成，独立自研才获得继续举证的资格。

这不是保证结论正确的分数，而是防止证据空白被解释成扩大投入的理由。no-go 条件说明何时不应继续，升级条件说明还需什么证据，复查触发器则在目标用户、核心场景、定位、关键依赖或替代生态实质变化时使旧结论进入待复核状态。

## grader-only sidecar

`PROJECT_VIABILITY` 是确定性评分入口使用的 sidecar。它把四个价值维度、两遍搜索、候选与来源引用、最强替代试用、独立反方和承诺上限组织成可检查结构，供 fixture、grader 和 repository validator 防回归。

它不是运行时状态、用户报告、第五个 core schema，也不嵌入 DecisionRecord。Consent 与 receipt 仍是授权和执行事实的唯一机器来源；sidecar 只引用它们，不复制第二套事实。canonical DecisionRecord 继续用已有字段表达判断、条件、现实实验、反转信号和复查触发器。

## 静态证据与真实执行边界

Schema、fixture、grader、rubric 和线框可以证明合同已定义、引用一致、授权关系可机械检查，并能拒绝一组已知坏结构。它们不能证明：

- 真实搜索覆盖了全部重要候选；
- 来源可信、及时或语义充分；
- 被标记为最强的候选确实最强；
- 现实试用真的执行、任务具有代表性或结果真实；
- 额外 Agent 具有认知独立性；
- 自然语言自动发现、原生 UI 或某个 runtime 已通过。

这些事实只能由绑定准确版本的真实 capability observation、consent、trace、receipt、用户报告和经审阅 evidence 建立。未运行继续标记为 `not_run`，拒绝、失败和无法访问继续保留为未知。

## 分发与发布边界

`skills/think-it-through/` 仍是唯一运行时维护源。`distribution/package-manifest.json` 是 `.skill` 归档精确文件集合的唯一机器事实源；v0.4.0 新增的 `references/project-viability.md` 进入运行时包，`evals/`、项目可行性 sidecar fixture、compatibility、benchmark 和本机配置不进入。

v0.4.0 的稳定源码身份由正式合同、schema、fixtures、grader、文档和确定性校验共同建立；其公开发布身份由同名不可变 Git tag、GitHub Release、可下载 `.skill` 与 `SHA256SUMS` 共同建立。两种身份都不替代 runtime/version 级兼容证据；v0.3.0 继续作为历史发布保留。
