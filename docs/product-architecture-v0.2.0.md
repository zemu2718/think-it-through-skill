## 0. 执行摘要

### 最终建议

不要把 Think It Through 重构为“方法大全”“虚拟专家会议”或“默认联网的多 Agent 平台”。最佳方向是把它升级为一个**重要行动前后的决策与证据协议**：

```text
用户准备让 AI 或自己采取重要行动
→ 先校准真实目的和当前决定
→ 判断缺的是用户选择、外部事实、独立反证，还是真实世界反馈
→ 以最低充分成本选择单 Agent、按需调研、多 Agent 或真人参与
→ 给出一个有条件的解决方案和主承诺
→ 用现实证据复判
```

产品的长期差异化不在拥有多少思考框架，而在七件事能否稳定成立：

1. 不让 AI 高质量地完成错误任务；
2. 不把用户价值选择伪装成外部事实；
3. 方法路由由系统承担，但用户始终看得懂当前角度、认得出正式方法名，并能通过交互确认或调整最终组合；
4. 该查的事实不反复要求用户自己查，也不在缺证据时假装已经知道；
5. 多 Agent 只为独立增量工作服务，不用数量和投票制造权威；
6. 无论调用多少能力，最终都交付一个综合后的解决方案、反转条件和现实下一步；
7. 决策、证据、授权和结果能够跨轮次复判，而不是生成一份看完即失效的报告。

### 产品定位

推荐的一句话定位：

> **在你让 AI 或自己投入重要资源之前，帮你确认真正要解决什么、还缺哪类关键证据，并给出可复判的解决方案与下一步。**

更短的品牌表达仍可保留：

> **别让 AI 把错误的任务完成得无比漂亮。**

### 首要用户

首要 ICP 应继续聚焦：

- AI 原生的一人公司、小微企业经营者；
- 独立开发者与小团队负责人；
- 同时承担产品、技术、营销、销售与交付判断的人。

他们拥有较高行动自主权，却缺少完整研究、战略与反方审查团队；一次错误投入会挤占其他路径。他们也最容易让 AI 从“模糊意图”直接进入“高质量执行”。

团队、职业、合作与关系场景可以继续支持，但不应同时成为早期市场传播的同等主叙事。**产品能力可以通用，首发定位必须聚焦。**

### 最重要的版本判断

- **保留 v0.1.5 的核心优势**：目的对齐、可并存目的先合并、方法透明且由用户确认、一个决策敏感答案槽、明确判断、一个现实证据闭环、授权分离、语义分段和终端可读性。
- **v0.2.0 已正式发布**：证据路由、参与路由、用户总参与 Agent 上限、判断前的有界调研、真人参与、决策快照、复判语义、四类授权、能力协商和宿主 Adapter 已进入正式协议。
- **不把能力层塞进方法注册表**：调研、多 Agent、真人参与和跨宿主适配不是普通方法卡。
- **不默认扩大流程**：简单、低风险、可撤回的问题仍直接回答或执行；Gate 由问题需要、能力状态和用户授权共同决定。

## 1. 演进基线：v0.1.5

### 1.1 已完整实现的用户闭环

v0.2.0 设计开始时，v0.1.5 已经实现：

```text
说出议题
→ R-align：对齐希望得到或保护的结果
→ R-method：确认最小必要思考角度
→ A：只回答一个会改变决定的问题
→ B：获得明确判断和一个现实实验
→ 纠正、新事实或不同意见触发新一轮
```

v0.1.5 的主要升级是回复话术和终端呈现，包括：

- 根据答案形态选择多选、单选或开放回答；
- 多个目的可以并存时先合并，不强迫排出唯一第一名；
- 不自行制造“第一版只能做一件事”等虚假排他约束；
- 自由文字可以纠正原生选择，冲突时以文字为准；
- 方法说明、操作提示和正式问题不再挤成长复句；
- 一意一段，问题独立位于末段，B 的动作、观察与复判易于终端扫描；
- UX rubric 增至十维、20 分，并把终端可读性列为必过维度。

### 1.2 发布范围与执行事实分层

v0.2.0 将三个层次分开管理：

```text
发布支持范围：正式入口、纯文本基线和条件能力边界
仓库合同质量：schema、fixture、评分器与发布校验
具体会话执行：能力观测、授权、trace、receipt 与降级
```

这避免两种相反错误：不能因某个 Adapter 或 Schema 存在就推定宿主能力，也不能因条件能力未在某次会话启用就把正式协议描述成未完成。

### 1.3 v0.2.0 发布能力

以下能力已经进入 v0.2.0 源码、schema、policy、adapter、评分器、fixture 和正式合同：

- A 回答后按需进入有界市场或事实调研；
- 由用户设置包含主 Agent 的总参与上限；
- 按问题路由当前主 Agent、额外 Agent 或真人参与；
- 对独立增量任务进行多来源调研、反证与来源审计；
- 建立纯文本、Claude Code 和 ChatGPT 的宿主适配合同；
- 默认生成对话内决策快照，并定义授权持久化与结果复判；
- 保留与规格澄清类 Skill 的标准化上下游边界。

v0.2.0 的正式入口是 Claude Code 中显式调用 `/think-it-through`，纯文本协议是跨宿主基线。原生 option UI、Evidence Gate、额外 Agent、真人参与、持久化等条件能力只在当前会话实际提供、满足路由条件并取得对应授权时启用；发生与否由 trace 和 receipt 建立。ChatGPT Adapter 定义 Skill-only / 纯文本语义映射，不构成原生兼容认证。

## 2. 从目标用户出发重新定义问题

### 2.1 首要 JTBD

当我准备让 AI、自己或团队对一个重要方向投入时间、金钱或声誉时，帮助我：

1. 先确认眼前动作是否服务真实目的；
2. 看清现在真正需要决定什么；
3. 分清哪个未知应问我、哪个事实应由系统查、哪个问题只能靠真实行动回答；
4. 获得一个不是观点拼盘的综合判断；
5. 只承诺一个能产生新证据、保留回头空间的下一步；
6. 在结果出现后知道继续、调整、暂停还是停止。

### 2.2 用户不是来“使用方法”的

用户真正购买或采用的不是双向钢人、失败预演或更多思考术，而是：

- 减少错误方向上的高质量执行；
- 减少不必要的全面投入；
- 更快定位真正会改变决定的证据；
- 在不完整信息下仍能形成可行动判断；
- 降低被 AI 的流畅表达、推荐答案或虚假确定性带偏的概率；
- 保留对价值、风险和外部行动的最终控制权。

因此，新增功能的门槛应是“是否改善决定或复判”，不是“是否增加框架、角色、报告或调用量”。

### 2.3 主要替代方案

目标用户今天通常会使用：

1. 直接问通用 AI，让它给建议或方案；
2. 让 AI 做一份市场研究或竞品报告；
3. 使用商业画布、SWOT、六顶思考帽等模板；
4. 找朋友、合伙人、顾问或团队会议讨论；
5. 直接做产品、投放或联系客户，用结果倒逼答案；
6. 使用 `grill-me / grilling` 一类访谈 Skill 把计划问完整。

Think It Through 的机会不是比这些方案“包含更多”，而是成为它们之前的路由器和之后的复判器：**现在到底缺哪一种工作，做到什么程度才足以改变决定。**

## 3. 已采用的四层模型：决定、证据、参与、宿主与行动

为避免把能力工作流误当成方法卡，v0.2.0 采用四层结构：

```text
1. Decision Core（决定层）
   真实目的、当前决定、竞争判断、关键变量、判断与反转条件

2. Evidence Policy（证据层）
   用户事实、公开事实、私有数据、专业意见、现实行为证据

3. Participation Policy（参与层）
   单 Agent、多 Agent、真实利益相关者、专业人士

4. Host & Action Adapter（宿主与行动层）
   Claude Code、ChatGPT、纯文本；控件、搜索、文件、发送与持久化
```

### 3.1 Decision Core

必须保持宿主无关，负责：

- 表面任务 → 真实目的 → 决策问题；
- 目的是否充分、是否存在真实价值冲突；
- 方法最小路由、当前价值说明、最终组合确认与综合；
- 证据状态与分歧类型；
- 一个决策敏感变量；
- 一个综合判断、成立条件与反转条件；
- 一个共享同一假设的现实证据闭环；
- 本轮完成或重新进入对齐的条件。

它不应依赖 `AskUserQuestion`、某个模型、某个平台、某种 UI、固定 Agent 数量或联网能力。

### 3.2 Evidence Policy

负责判断“答案应该从哪里来”：

| 关键未知类型 | 默认来源 | 产品动作 |
| --- | --- | --- |
| 用户目的、底线、风险承受 | 用户本人 | 只问一个最敏感的问题，不让 Agent 代答 |
| 团队权责、承诺、利益冲突 | 对应真实参与者 | 生成一个具体参与请求，未经授权不发送 |
| 公开且可核实、具有时效性的事实 | 有界调研 | 获取来源、日期、反例和限制 |
| 私有业务事实 | 用户授权的数据源 | 最小范围读取，单独取得数据访问授权 |
| 专业高风险判断 | 合格专业人士 | 整理咨询重点，不由多个 Agent 投票替代 |
| 只能通过真实反应获知 | 现实实验 | 原型、访谈、预售、人工交付或其他行为证据 |
| 深度不确定、不可可靠预测 | 稳健性设计 | 优先可逆、分阶段承诺和适应策略 |

### 3.3 Participation Policy

负责判断谁参与、为什么参与、最多多少 Agent。它不是方法路由，也不改变最终责任：

- 默认单 Agent；
- 必要时增加独立调研者、挑战者或证据审计者；
- 权责、价值和承诺分布在多人时，邀请真人参与；
- 主 Agent 始终负责去重、证据校准、冲突呈现和最终综合；
- Agent 结果是材料，不是投票权威。

### 3.4 Host & Action Adapter

负责把核心意图映射到宿主能力：

- 选择、多选、自由回答或四项反馈路由；
- 公开搜索、文件读取、私有连接器；
- 子 Agent、并行任务或服务端编排；
- 会话状态、决策快照和用户偏好；
- 草稿、发送、发布、购买或其他外部行动；
- 权限、失败回执和文本降级。

## 4. 用户可见体验：不是复杂模式菜单，而是渐进升级

### 4.1 五种渐进体验深度

这些是产品内部路由或简洁的用户选择，不是五套完全不同的产品。

#### A. 直接处理

适用于已决定、低风险、规格清楚且可撤回的任务。直接回答或执行，不启动完整决策流程。

#### B. 快速检查

适用于目的基本清楚、信息足够、风险中低的选择。压缩呈现但保留核心语义：

```text
真正要决定什么
→ 一个关键答案
→ 一个判断
→ 一个下一步
```

不等于跳过用户回答边界，也不允许 AI 自问自答。

#### C. 深度决策

即 v0.1.5 的完整优势路径：目的对齐、角度确认、唯一问题、判断和现实实验。默认仍由单 Agent 完成。

#### D. 调研增强

当关键未知是可公开核实且会反转判断的外部事实时，在最终 B 判断前插入有界证据门。它不是“先做完整市场报告”，而是只查对决定敏感的证据。

#### E. 协作增强

当任务确实可独立并行、需要反锚定，或真实信息和权责分布在多人手中时，启用多个 Agent 或真人参与。最终仍回到一个综合判断和一个主证据闭环。

#### F. 结果复判

当用户已经执行并产生结果时，读取或粘贴上次决策快照，比较预期、事实、成本与意外后果，给出继续、调整、暂停或停止。

### 4.2 不应一开始让用户配置所有模式

普通用户不应先理解“调研模式、协作策略、Agent 拓扑、证据 frontier”。推荐体验是：

1. 默认以最低成本路径开始；
2. 当系统识别出明确增量价值时，解释为什么需要升级；
3. 只展示与当前问题有关的一次选择；
4. 用户可接受、降低上限、改为单 Agent，或停止；
5. 没有升级价值时不出现配置。

### 4.3 方法确认继续是核心体验，优先采用单屏内联推荐

用户不是来学习方法目录的，但这不等于系统可以隐藏实际采用的思考角度。目的与当前决定清楚后，v0.2.0 推荐把理解和选择合并到同一个交互单元：

```text
系统筛选 0～3 个与当前议题相关的方法
→ 为每个候选生成“正式方法名 + 推荐状态 + 当前价值”
→ 宿主支持选项说明时，直接内联到同一个选择控件
→ 用户一次提交唯一最终组合
→ 自由文字仍可加入、取消、替换或纠正
```

推荐的用户可见形态：

```text
你现在真正要决定的是：先验证谁的需求，以及是否继续当前方向。

基本梳理始终包含，不需要选择。

我标出了当前更建议采用的角度。

可多选，也可以直接加入、取消、替换或纠正。

这轮保留哪些额外思考角度？

☐ 对象校准（推荐）
  分清使用者、付费者和承担代价的人，帮助判断应该先验证谁的需求。

☐ 双向钢人（推荐）
  用相近的证据标准检验当前方向和最强替代方向，避免只证明已有倾向。
```

复选框只是语义示意；原生多选可用时必须真实调用。控件前只保留当前决定、基本梳理和必要操作提示，不再先完整解释一遍方法，再在控件中重复列出名称。正式方法名、推荐标记、当前价值和选择入口应尽量出现在同一个选项中。

`推荐` 只表示系统当前建议，不构成用户确认。只有用户实际提交的勾选集合或明确的自由文字，才形成唯一最终组合；默认勾选、浏览候选或打开控件都不能被当作确认。

未标记为推荐的方法只有在它仍与当前议题相关、具有独特增量时才可作为备选出现，并且同样必须说明当前价值。没有合理备选时只显示推荐项，不为丰富界面凑满数量；列表外的方法仍可通过自由文字加入。

若宿主不能在选项中可靠呈现 description，则降级为紧邻的编号说明和一次文本选择；若没有结构化控件，则使用语义等价的纯文本路径。降级可以改变版式，不能省略正式名称、推荐状态、当前价值或最终组合提交。

这套设计同时解决三个问题：

- **降低理解成本**：用户在一个位置完成理解、比较和选择，不必在推荐段与控件之间来回对应；
- **保持方法透明**：正式方法名和推荐状态可辨识，用户知道系统建议什么、实际采用什么；
- **保留用户控制**：系统负责筛选和推荐，用户负责提交最终组合，并可精确调整。

v0.1.5 采用“控件前解释推荐理由、控件内只放简短正式名称”的合同；v0.2.0 将单屏内联推荐纳入正式合同。它优化的是信息位置和扫描成本，不改变目的清楚后才推荐、少量相关候选、方法必须确认、自由文字可纠正以及被取消方法不得暗中执行等核心语义。

## 5. 判断前市场调研：从固定时序改为证据路由

### 5.1 为什么要调整 v0.1.5 固定时序

v0.1.5 规定 R 和 A 不调用外部能力，B 先判断，再建议最小外部验证。这有效防止了无止境搜索，也保证无工具时仍能完成判断。

但它对以下问题过于严格：

- 当前竞品、价格、法规或平台政策会直接改变是否进入市场；
- 用户问的是特定市场是否已有强替代方案；
- 某项公开事实如果为真，候选路径会直接反转；
- 用现有信息先给“最终判断”会产生没有必要的猜测。

v0.2.0 应保留“调研不是默认依赖”，同时允许**在最终判断前做一次有界调研**。

### 5.2 已采用 Evidence Gate

采用的状态语义：

```text
R-align
→ R-method
→ A：获得用户掌握的决定敏感答案
→ Evidence Gate：仅在必要时调研
→ B：综合用户答案与外部证据后判断
```

Evidence Gate 不是所有议题都经过的第四阶段，而是条件能力。只有以下条件全部成立才进入：

1. 当前未知是外部可验证事实，不是用户价值或底线；
2. 至少两个合理答案会改变方案排序、是否继续或投入边界；
3. 事实具有市场、时间、地区、法规或当前替代方案依赖；
4. 有明确且范围受限的获取方式；
5. 预期证据价值高于成本、延迟和隐私风险；
6. 已取得本次具体能力授权；涉及私有数据或外部联系时另取对应授权。

### 5.3 不应前置调研的情况

- 用户还没说清自己真正要什么；
- 关键分歧是价值选择或风险偏好；
- 搜索只会增加背景知识，不会改变决定；
- 现实行为实验比二手资料更直接；
- 议题低风险且容易撤回；
- 来源不可得、噪声过高或成本不相称；
- 调研成为推迟决定的借口。

### 5.4 调研合同

一次调研增强至少记录：

```text
要改变的决定：
关键证据问题：
范围：市场 / 地区 / 时间 / 对象：
停止条件：什么程度的信息已经足够：
来源要求：一手来源优先，必要时交叉核验：
支持证据：
反对证据：
冲突与空白：
证据日期：
对判断的影响：改变 / 不改变 / 仍不确定：
```

完成标准不是“搜了很多”，而是：

- 决定敏感的问题已得到足以区分候选方向的回答；或
- 继续搜索的边际价值已低于成本；或
- 已确认二手资料无法回答，应转为现实实验。

### 5.5 调研失败时必须继续

能力不可用、被拒绝、超时、来源冲突或没有可靠答案时：

- 不虚构结果；
- 把该项保留为关键未知；
- 仍基于现有信息给有条件判断；
- 降低承诺、提高可逆性或转向现实实验；
- 不把用户困在“等调研完成”状态。

## 6. 多 Agent：默认单 Agent，按独立增量升级

### 6.1 多 Agent 的正确价值

多 Agent 只有在工作能够真正拆成相互独立的部分时有价值，例如：

- 不同市场、来源或法规可并行检索；
- 候选解释需要独立形成，避免共享叙事锚定；
- 需要一个 Agent 专门尝试推翻候选结论；
- 需要证据审计者核对来源、冲突和遗漏；
- 研究任务足够大，并行能显著降低等待时间。

Claude Code 官方文档也把子 Agent 定义为拥有独立上下文、特定工具和权限的专门助手，适合把会淹没主对话的搜索、日志或文件内容隔离出去。它们能节省上下文并加强工具约束，但这不等于“更多 Agent 自动带来更好判断”。

### 6.2 不应启用多 Agent 的情况

- 用户的目的还没清楚；
- 简单、低风险、可撤回的问题；
- 任务无法拆成不重复的独立工作；
- 只是让多个 Agent 复述同一框架；
- 让多个模型投票代替事实或用户价值；
- 增加 Agent 只会制造“专家会议”观感；
- 成本、延迟、隐私负担高于可能的决策增益。

### 6.3 设置原则：用户定上限与边界，不管理 Agent 团队

普通用户不应先配置角色、拓扑、并发和调度策略。多 Agent 设置只回答四件事：是否允许按需升级、最多允许多少、偏好保存多久、可使用哪些数据与能力。具体拆分和调度由系统承担。

#### 协作偏好

```text
协作增强：关闭 / 按需询问 / 在上限内自动
总参与 Agent 上限：包含当前主 Agent
偏好范围：仅本次 / 本会话 / 保存为默认
```

默认建议：

- 协作增强：`按需询问`；
- 总参与 Agent 上限：首次确有需要时结合独立任务给出建议，不预设跨宿主固定数字；
- 偏好范围：默认仅本次或本会话；长期保存必须由用户主动开启，并允许查看、修改和删除；
- `在上限内自动` 只代表不再重复询问是否增加 Agent，不能继承联网、私有数据或外部行动授权。

数量表达必须同时显示总数和增量，避免“3 个 Agent 是否包含当前 Agent”的歧义：

```text
总参与 Agent：4 个
├── 当前主 Agent：1 个
└── 额外 Agent：3 个
```

用户设置的是硬上限，不是系统应当用满的目标。额外 Agent 不得继续自行递归委派；若产生新的委派需要，必须重新计入上限和本次方案，不能绕过用户限制。

#### 能力与授权分离

必须明确：

```text
允许多 Agent
≠ 允许公开联网
≠ 允许读取私有数据
≠ 允许发送、发布或修改外部世界
```

公开联网可另设为`允许 / 每次询问 / 不允许`；私有数据始终按具体资源和最小范围单独授权；发送、发布、购买、删除、联系客户等外部行动始终另行确认。分发给每个额外 Agent 的上下文也应按任务裁剪，不把完整私有会话复制给所有 Agent。

### 6.4 本次启用：单屏说明具体增量

只有识别出明确并行价值时，才展示一次本次协作方案。用户看到的应是具体任务、数量、数据边界和降级方式，而不是抽象的“专家角色”。例如：

```text
这一步有明确的并行价值。

我建议让 3 个额外 Agent 分别处理：

1. 核对当前市场、价格和主要替代方案
2. 查找目标用户需求与真实行为证据
3. 独立挑战初步结论并检查来源遗漏

当前主 Agent 负责最终综合，不按多数票决定。

本次预计：
- 总参与 Agent：4 个，包含当前主 Agent
- 额外 Agent：3 个
- 数据范围：仅公开网页
- 私有文件：不读取
- 外部行动：不会发送、发布或联系任何人
- 影响：增加模型调用量；并行通常能减少等待时间
- 降级：任一 Agent 失败，主 Agent 仍基于有效材料继续

本次怎样处理？

○ 按建议启用 3 个额外 Agent（推荐）
○ 降为 2 个额外 Agent
○ 保持单 Agent
```

选项互斥时使用宿主原生单选，并保留自由输入。用户可以直接说“最多两个，只做市场和反证”或“可以用三个，但不要读取项目文件”。停止本轮也应是同等可用的自由选择，不通过恐吓式文案推动启用。

若宿主无法提供可靠的时间、token 或费用估算，不制造精确数字；改为说明相对调用增量、可能的延迟变化和不确定性。只有真实可用的宿主计量信息才能作为具体估算来源。

### 6.5 实际数量的计算

为消除口径歧义，建议把用户上限定义为**包含当前主 Agent 的总参与上限**，并单独计算额外 Agent：

```text
可用额外 Agent 上限 = max(0, 用户总参与上限 - 1)

实际额外 Agent 数 = min(
  独立增量任务数，
  可用额外 Agent 上限，
  产品额外 Agent 安全上限，
  宿主可用额外 Agent 上限，
  成本与延迟预算允许数量
)

实际总参与 Agent 数 = 1 + 实际额外 Agent 数
```

如果只有一个独立增量任务，即使用户允许十个总参与 Agent，也只增加一个。若没有独立增量任务，则保持当前主 Agent，不为了使用额度而创建工作。

### 6.6 前台显示具体任务，角色只作为内部能力标签

不建议让用户维护固定的“市场专家、战略专家、风险专家”团队。根据问题临时选择以下能力，不常驻：

- **研究者**：只回答一个有界证据问题并保留来源；
- **竞争解释者**：独立构造最强替代判断；
- **挑战者**：以推翻当前候选结论为目标；
- **证据审计者**：核对来源质量、冲突、遗漏和反转条件；
- **综合者**：当前主 Agent，负责去重、权衡证据、标记不确定性并交付最终结果。

用户前台看到“核对德国市场当前法规”这类具体任务；“研究者”只作为内部调度标签。每个额外 Agent 都必须有不重复、可验证、可停止的独立任务，并返回结构化材料：

```text
assigned_question
claims
evidence_and_sources
assumptions
uncertainties
conflicts
what_would_reverse_this
```

### 6.7 在流程中的启用位置

多 Agent 是参与能力，不是方法卡。默认时序建议为：

```text
R-align：主 Agent 对齐真实目的
→ R-method：用户确认本轮思考角度
→ A：用户回答唯一决策关键问题
→ Evidence / Participation Gate：识别外部证据或独立反证缺口
→ 必要时展示本次多 Agent 方案
→ 用户确认数量、任务和数据边界
→ 额外 Agent 执行独立工作
→ 主 Agent 综合后进入 B
```

目的和当前决定未清楚前不启动多个 Agent。用户即使一开始明确要求“用多个 Agent 调研”，也应先完成最小必要对齐，再把真实决策问题转成具体协作方案；不能让多个 Agent 更快地研究错误问题。

### 6.8 运行中只展示统一任务进度

额外 Agent 不分别向用户发表长篇意见，也不争夺主对话。宿主支持进度呈现时，使用一个简洁的任务视图：

```text
协作增强：3 个额外 Agent

✓ 市场与价格证据
✓ 主要替代方案
◌ 独立反证与来源审计

主 Agent 将在材料返回后统一综合。
```

进度只表示执行状态，不表示证据质量或结论置信度。用户应能看到实际启动数量，并可在宿主支持时停止尚未完成的额外工作；停止不应删除已经得到的有效材料，也不应自动触发外部行动。

### 6.9 完成后给协作回执

进入最终判断前或写入决策快照时，给出简短、可审计的协作记录：

```text
本次协作记录

计划额外 Agent：3 个
实际启动：3 个
完成：2 个
失败：1 个
使用数据：公开网页
私有数据：未访问
外部行动：未执行

主要分歧：
- 市场规模证据支持继续验证
- 付费意愿证据仍不足
- 独立反证任务未完成，因此没有提高结论置信度
```

回执不要求暴露隐藏思维链，只记录任务、来源、状态、权限使用、关键冲突和缺失工作。计划数与实际数不同、能力失败或用户中途降低上限时，必须如实记录。

### 6.10 综合规则

- 不按多数票决定；
- 不把模型一致性当成真实世界事实；
- 相同来源的多个转述只算一份证据；
- 分歧必须追溯到事实、预测、价值、约束或风险偏好；
- 用户价值和底线始终交回用户；
- 主 Agent 明确哪些材料被采用、舍弃或仍冲突；
- 最终只给一个综合判断和一个主现实证据闭环。

### 6.11 失败与降级

某个 Agent 超时、失败、权限不足或输出低质量时：

- 保留其他有效材料；
- 标记缺少的工作，而不是补造结果；
- 在统一进度和最终回执中如实呈现；
- 主 Agent 在现有证据下继续；
- 必要时从多 Agent 降为单 Agent；
- 不因“团队未齐”阻塞最终判断。

## 7. 真人多人：Agent 不能替代利益相关者

### 7.1 什么时候需要真人参与

真实参与者掌握以下内容时，应优先邀请对应的人，而不是继续增加 Agent：

- 决策权或预算承诺；
- 受影响者的价值与底线；
- 团队内部真实权责和执行承诺；
- 客户是否愿意付费或改变行为；
- 专业高风险事实与责任；
- 合作方愿意接受的边界和退出条件。

### 7.2 多 Agent 与真人多人不能混为一谈

| 多 Agent 能做 | 多 Agent 不能替代 |
| --- | --- |
| 并行查公开事实 | 客户真实购买承诺 |
| 独立形成竞争解释 | 合伙人的边界与承诺 |
| 尝试反驳候选判断 | 团队负责人最终拍板 |
| 审计来源和遗漏 | 持证专业意见与责任 |
| 压缩大量材料 | 受影响者本人表达的价值 |

### 7.3 真人参与最小合同

```text
为什么需要这位参与者：
只请对方回答什么：
需要共享哪些最小背景：
哪些私有内容不共享：
回答如何改变判断：
由谁负责发送和收集：
```

默认只生成可转发材料。向外发送、邀请、创建群聊或联系客户都属于外部行动，需另行确认。

### 7.4 团队场景的最终产出

多人场景不应变成“每个人说完就算完成”。最终要明确：

- 共同事实与仍有争议的事实；
- 不可由事实消除的价值或利益冲突；
- 谁拥有哪个决定权；
- 谁承诺什么；
- 下一步检验哪个共同假设；
- 什么结果触发重新协商、暂停或退出。

## 8. 给用户“解决方案”，不是只给流程

### 8.1 解决方案合同

v0.2.0 的最终交付应自然包含：

1. **当前判断**：推进、验证、调整、暂停或停止；
2. **推荐方向**：此刻应选择什么，而不是只列选项；
3. **为什么**：最关键事实、推断、假设和用户价值；
4. **成立条件**：结论在哪些边界内有效；
5. **反转条件**：什么证据会让判断改变；
6. **主承诺**：现在只做的一件事；
7. **观察**：什么现实信号支持或反对继续；
8. **复判**：依据什么重新决定；
9. **必要的证据来源**：如果使用调研或多人材料，给可追溯引用；
10. **用户控制**：不自动进入外部执行。

“给解决方案”不意味着：

- 替用户选择价值和底线；
- 在事实不足时伪装确定；
- 把多个 Agent 的投票当结论；
- 未经授权自动实施；
- 为显得完整而提供大而全路线图。

### 8.2 一个现实实验的语义应放宽，而不是删除

应保留“一个主证据闭环”，但不要把它机械理解为：

- 只能一个参与者；
- 只能一个物理动作；
- 不能使用多个 Agent；
- 不能包含必要的连续操作。

正确判定是：所有操作是否共同检验**同一个核心假设**、共享同一资源边界、观察标准和复判点。机器层继续保留 `core_hypothesis / action / observation / reassessment` 四个稳定角色；显示层先用自然句说清含义，再按需后置受控标记。这样既不会把必要连续操作误判成多个实验，也不会让句首术语标签主导用户阅读。多个互不相关项目不得被包装成一个实验。

### 8.3 快速模式与深度模式都必须交付结果

快速模式不应只“提醒想清楚”，深度模式也不应只“展示分析”。两者都必须在信息允许时给明确方向。区别只在证据深度和互动成本，不在是否承担综合判断责任。

## 9. 决策快照与长期复判

### 9.1 为什么这是比继续加方法更重要的能力

一次决策的真实质量只能在结果出现后部分观察。若不保存当时的目的、假设、证据和反转条件，用户容易：

- 用结果反写当时理由；
- 因沉没成本继续；
- 把执行偏差误判为方向错误；
- 忘记原先约定的停止信号；
- 下一次重复同类错误而无法校准。

### 9.2 默认输出轻量 Markdown 快照

DecisionRecord 的机器 key 必须稳定，才能持续校验、迁移和复判；用户可见快照则是可本地化的自然语言显示投影。自然化不等于语义松散：每个显示字段仍要无损映射 canonical path，尤其不能合并假设与未知。

```markdown
## 决策快照

这次要想清楚的事：
真正想得到或保护的结果：
本轮需要决定什么：
本轮采用的思考角度：
目前更合适的方向：
为什么这样判断：
判断成立的前提：
已经确认的信息：
根据现有信息可以推断：
当前判断仍依赖：
仍不知道的关键问题：
本轮依据来自哪里：
什么情况会改变判断：
要弄清什么：
先做什么：
看哪些现实信号：
什么时候重新决定：
本轮参与者与使用的能力：
这份记录保存在哪里：仅在当前对话中
```

current grader 检查主现实闭环的受控句末标记，而不依赖固定标题或句首标签；canonical schema 仍负责机器记录本身。

### 9.3 保存策略

- 默认只在对话中生成可复制 Markdown；
- 写入文件、云端或账号需要明确授权；
- 区分临时 UI 状态、会话记录、决策记录和长期偏好；
- 不保存隐藏思维链，只保存复判所需的简明依据；
- 用户应能查看、导出、修改和删除；
- 无持久化能力时，用户可在下一次粘贴快照恢复。

### 9.4 复判流程

```text
读取原决策快照
→ 对比预期信号与真实结果
→ 区分判断错误 / 执行偏差 / 资源错配 / 条件变化
→ 重新确认目的是否仍成立
→ 给出继续 / 调整 / 暂停 / 停止
→ 更新快照
```

## 10. 跨平台：Portable Decision Core + Host Adapters

### 10.1 原则

v0.2.0 通过 Claude Code 中显式调用正式分发，并以纯文本协议作为跨宿主基线。新增宿主原生兼容范围时遵循：

```text
Portable Decision Core
├── 状态与语义
├── 方法和证据纪律
├── 调研与参与策略
├── 判断、现实实验与快照
└── 授权语义

Capability Negotiation
└── 检测当前会话真实具备什么

Host Adapters
├── Claude Code
├── ChatGPT / OpenAI plugin
└── 纯文本参考实现及其他宿主
```

### 10.2 核心发出语义意图，不发专有工具名

示例：

```json
{
  "kind": "request_selection",
  "selection": "multiple",
  "prompt": "这件事你主要希望获得哪些结果？",
  "options": [
    {"id": "portfolio", "label": "练手并做成作品"},
    {"id": "real-problem", "label": "解决一类人的具体问题"}
  ],
  "allow_free_text": true
}
```

核心只表达“多选且允许自由纠正”，不指定 `AskUserQuestion`、ChatGPT widget 或 Markdown。方法确认同样拆成宿主无关语义：每个候选携带正式方法名、推荐状态和当前价值，选择意图要求提交唯一最终组合，并允许加入、取消、替换或纠正。Adapter 在能力允许时把这些信息内联到同一个选项，只能改变交互表面，不能删除字段或确认语义。

建议的意图至少包括：

```text
request_free_text
request_selection
present_method_recommendation
request_method_selection
present_decisive_question
request_research_consent
request_agent_consent
request_private_data_consent
request_external_action_consent
delegate_analysis
request_human_review
present_judgment
present_decision_snapshot
persist_decision_snapshot
request_feedback
```

### 10.3 运行时能力协商

不能根据宿主名称猜能力，应逐项检测：

```text
interaction.free_text
interaction.select_one
interaction.select_many
search.public_web
search.private_corpus
tools.read
tools.write
agents.subagent
agents.parallel
humans.request_review
persistence.session
persistence.case
permissions.tool_call
permissions.private_data
permissions.external_action
fallback.text
```

每项能力同时记录：

- `available / unavailable / unknown`；
- `ready / requires_approval / requires_auth / failed`；
- provider、限制、来源和执行回执。

`unknown` 不能当作可用；“官方产品支持”也不能证明当前会话已经启用。

### 10.4 Claude Code adapter

当前可映射：

- 原生单选/多选 → 当前会话真实可用时调用 `AskUserQuestion`；
- 公开研究 → 实际存在且获准的 WebSearch、WebFetch 或 MCP 工具；
- 子 Agent → `Agent`，每个子 Agent 独立上下文、工具和权限；
- 复杂编排 → 只有用户明确同意且 Workflow 能力存在时使用；
- 失败或拒绝 → 立即文本降级，不用 Markdown 冒充调用成功。

Claude Code 子 Agent 官方能力证明的是隔离上下文、工具约束、专门化和上下文节省，不证明多 Agent 必然提高结论质量。子 Agent 也不能直接代替主线程向用户提问，因此用户控制和最终综合必须留在主线程。

### 10.5 ChatGPT / OpenAI adapter

截至本文基线，OpenAI 官方把 Skill 定义为由 `SKILL.md`、可选 references、scripts、templates 和 assets 组成的工作流层；MCP server 负责实时信息、认证、授权和受控行动。Skill 可独立工作，也可指导模型组合 MCP 工具。

因此推荐逐步采用：

```text
ChatGPT / OpenAI plugin
├── portable Skill instructions
├── 可选 MCP server：搜索、数据、持久化、服务端编排
└── 可选自定义 UI：单选、多选与纠正
```

必须保持事实边界：

- 不能因为 ChatGPT 支持 Skill 就假设它拥有与 Claude Code 完全相同的问答控件；
- 自定义 UI 是插件能力，不应冒充所有 ChatGPT 对话的通用原生能力；
- OpenAI Agents SDK 的多 Agent 编排属于应用或服务端运行时，不等于普通 ChatGPT Skill 可直接生成子 Agent；
- 宿主搜索、插件 MCP 搜索和 API Web Search 是不同 provider；
- UI 临时状态不等于长期决策记录；
- 无 UI、无搜索、无子 Agent 时仍必须能用纯文本完成核心流程。

### 10.6 纯文本参考实现是一等能力

纯文本路径不应只是残缺兜底，而应成为验证跨宿主语义的参考实现：

| 核心意图 | 纯文本呈现 |
| --- | --- |
| 单选 | 编号选项，并说明可直接纠正 |
| 多选 | 编号选项，并说明可多选或补充 |
| 方法推荐与确认 | 每项紧邻呈现正式名称、推荐状态和当前价值，再用一次文本选择提交组合；允许加入、取消、替换或纠正，并回显最终组合 |
| 开放回答 | 不预造选项，直接等待 |
| 四项反馈路由 | 普通编号表达四个稳定方向，并允许同一条消息补充；不使用伪控件 |
| 搜索不可用 | 给最小调研 brief，并基于现有证据继续 |
| 子 Agent 不可用 | 单 Agent 继续，不假装已咨询专家 |
| 真人协作不可用 | 生成可转发材料，不自动发送 |
| 持久化不可用 | 输出可复制决策快照 |

## 11. `grill-me / grilling` 与本项目的关系

### 11.1 先纠正产品事实

固定上游版本中：

- `grill-me` 是显式入口，正文只调用 `grilling`；
- `grilling` 才是完整的访谈 primitive；
- `grilling` 使用设计决策树和 frontier，目标是暴露并解决计划或设计中的隐含决策；
- 上游许可证为 MIT。

因此，不能只看 skills.sh 摘要就把所有能力都归给 `grill-me` 本体。

### 11.2 两者的核心差异

| 维度 | Think It Through | `grilling` |
| --- | --- | --- |
| 成功目标 | decision readiness：是否值得、选哪条路、什么证据会改判 | specification completeness：选定方向还有哪些设计决定未说清 |
| 问题策略 | 只索取决策敏感度最高的一个答案 | 处理当前 frontier，可能一轮多个问题、持续展开分支 |
| 结果 | 有条件判断 + 现实实验 + 复判 | 共同理解和更完整的设计规格 |
| 对“不知道” | 仍进入判断，降低承诺或做实验 | 往往继续分支、缩小范围或转向原型 |
| 调研 | v0.1.5 为 B 后最小验证；v0.2.0 建议有界 Evidence Gate | 可把环境中可查事实交给 sub-agent |
| 用户负担 | 最小必要交互 | 用户主动选择的深度访谈 |

### 11.3 最佳上下游关系

```text
Think It Through
→ 判断方向值得进入设计，明确条件与验证边界
→ grilling
→ 把已选方向中的设计依赖和规格问完整
→ 执行 Skill / Agent
```

也可以反向嵌套：当 `grilling` 的设计树遇到高成本分叉，例如自建还是采购、进入哪个市场、是否接受不可逆架构时，把该节点交给 Think It Through 判断，再把结果送回设计树。

路由建议：

- “值不值得做、A 还是 B、要不要继续、下一笔资源投哪里” → Think It Through；
- “把设计问透、找出所有未决规格、实现前彻底 challenge” → `grilling`；
- “stress-test this plan” → 先判断用户需要一个方向判断，还是规格完整性；
- 用户显式调用哪个就优先哪个，不擅自替换。

### 11.4 值得借鉴

1. **依赖感知**：前置条件未满足的问题不应假装可回答；
2. **证据 frontier / 人类决定 frontier 分离**：可查事实可并行，价值与底线留给人；
3. **事实由系统找、决定由人作**；
4. **识别只能由原型或现实反应回答的问题**；
5. **共同理解完成门**：但应改为“没有未处理且足以反转判断的关键节点”；
6. **入口与 primitive 分层**：但不能依赖隐式跨 Skill 调用作为唯一实现路径。

### 11.5 不应照搬

- `relentless` 的逼问式身份；
- 一轮询问整个 frontier；
- 每题附推荐答案导致锚定；
- “所有树枝访问完才结束”的穷尽标准；
- 默认派 sub-agent，且没有成本、授权、来源和失败治理；
- 固定编号、图标、分隔线和长批次 Markdown；
- 用问题数量、Agent 数量或上下文长度证明充分性。

### 11.6 采用与许可建议

本方案只建议借鉴抽象机制，不建议复制其措辞或完整流程。如果未来实质改编固定源码，应：

- 在第三方审计中记录仓库、固定 commit、采用文件和 MIT 许可证；
- 说明哪些机制被改写、哪些没有采用；
- 增加触发边界和重叠路由评测；
- 不因“同为 Skill”就宣称跨宿主行为等价。

## 12. 方法体系：暂缓扩卡，先建立四层治理

### 12.1 保留现有九项可选方法能力

继续保留：

- 双向钢人；
- 失败预演；
- 对象校准；
- 系统瓶颈；
- 阶段匹配；
- 资源支点；
- 边界契约；
- 沟通匹配；
- 证据闭环。

它们已经覆盖大量目标用户场景。短期差异化不来自继续扩充数量。

### 12.2 方法名与交互式选择是产品优势

方法体系应同时避免两个极端：一端是把完整目录和术语学习负担交给用户，另一端是把方法全部藏在后台，使用户无法知道或调整系统采用了什么。

v0.2.0 推荐合同是：

1. 系统先根据已经对齐的目的和当前决定筛选最小组合，不让用户从完整目录自行路由；
2. 每个候选都携带正式方法名、是否为系统推荐，以及它在当前议题中的具体价值；
3. 宿主支持选项 description 时，优先把这三类信息直接内联到多选项，不在控件前完整重复一遍；
4. 只呈现 0～3 个当前相关方法，不为了界面完整增加无关候选；非推荐备选也必须有独特增量和当前价值说明；
5. 方法可组合时使用原生多选；只有基础分析是唯一有效路径时，不伪造额外方法；
6. `推荐` 不等于 `确认`；用户提交的选择和自由文字共同决定唯一最终组合，可加入、取消、替换或纠正，冲突时以自由文字为准；
7. 后续只执行已确认的方法，不能把被取消的方法作为隐藏分析继续使用；
8. 确认后用自然语言简短回显组合，不展示内部方法 ID 或技术清单。

因此，v0.2.0 可以优化确认的**信息位置、呈现形式和轮次成本**，但不能把方法透明与用户确认本身当作可删除的摩擦。跨宿主变化的是原生控件、选项 description、文本降级、内嵌区域或独立页面；不变的是“正式方法名 + 推荐状态 + 当前价值 + 最终组合可确认、可调整”。

### 12.3 建议明确四层思考治理

```text
认知原则
→ 思考算子
→ 独立方法卡
→ 证据与协作工作流
```

#### 认知原则

例如奥卡姆剃刀、证据透明、可逆性、用户价值不可代答。它们是基础纪律，不应都做成可选方法。

#### 思考算子

例如逆向、约束移除、反事实、类比、分解。它们可以被方法内部调用，不应向用户展示成越来越长的菜单。

#### 独立方法卡

必须拥有明确输入、过程、独特产出、禁用边界和可测试路由。第一性原理若未来中性化为“约束重构”，需要证明它不只是基础分析的换名。

#### 证据与协作工作流

市场调研、多 Agent、真人多人、信息价值、稳健决策和规格澄清属于这一层，不进入 `methods/registry.yaml` 的普通方法列表。

### 12.4 后续方法候选的优先级

在真实用例证明现有能力存在稳定缺口后，再优先验证：

1. **信息价值**：决定是否值得继续获取信息，以及获取到何种程度；
2. **稳健决策**：多种未来都不可可靠预测时，选择跨情景不易后悔的路径；
3. **因果校验**：区分相关、机制和可干预因果，避免把市场共现当作行动依据；
4. **约束重构**：把用户自设限制与现实硬约束分开。

六顶思考帽更适合真人会议促进；汉隆剃刀更适合作为归因克制护栏；逆向思维更适合作为横向算子，而非都做成独立卡。

## 13. 对 v0.1.5 的保留、扩展、重构与不做

### 13.1 必须保留

- 先判断完整流程是否有额外价值；
- 表面任务、真实目的和决策问题三层模型；
- 不发明动机，不制造虚假排他；
- 可并存目的先合并；
- 选择与自由文字冲突时以文字为准；
- 方法少而必要；优先把正式名称、推荐状态和当前价值内联到同一个选择单元，并由用户确认或调整唯一最终组合；
- 只索取一个决策敏感答案槽；
- 判断明确且可被证据推翻；
- 一个主现实证据闭环；
- 四类授权分离；
- 语义分段和终端可读性；
- 不自动改变外部世界；
- 发布支持范围、仓库合同质量与具体会话执行事实分层记录。

### 13.2 应扩展

- 新增 Evidence Gate；
- 新增 Participation Policy；
- 用户可选 Agent 最大上限及会话偏好；
- 多 Agent 的独立任务、回执和综合合同；
- 真人参与的最小材料与授权；
- 决策快照和复判；
- Portable Decision Core 与 capability negotiation；
- Claude Code 和 ChatGPT adapter；
- 与 `grilling` 等规格 Skill 的上下游交接；
- 调研、协作、跨宿主和复判评测。

### 13.3 应重构为宿主特定约束

以下规则在 Claude Code v0.1.5 中有价值，但不应成为跨宿主永久产品定义：

- `AskUserQuestion` 具体工具名；
- A 整个文本恰好一个问号且必须是最后字符；
- B 完全不出现问号字符；
- 固定 Markdown 标题、粗体和方括号反馈；
- “一个实验”按物理动作或列表项计数；
- 方法确认必须占用独立页面或独占一个额外对话轮次。

跨宿主核心应保留其语义：一个答案槽、问后等待、B 不开启新信息请求、一个主证据闭环，以及方法的“正式名称 + 推荐状态 + 当前价值 + 最终组合确认与调整”。Adapter 应在宿主支持时把这些信息内联到原生多选项；不支持选项说明时再改用紧邻说明、内嵌文本或语义等价的纯文本路径。它不能因没有独立界面而隐藏方法、跳过最终组合提交，或把静态 Markdown 冒充原生工具调用。

### 13.4 暂不做

- 默认常驻的多 Agent 专家团；
- Agent 投票；
- 无上限的自主搜索；
- 默认读取所有私有数据；
- 自动联系客户、发问卷或发布内容；
- 完整方法市场；
- 持久化隐含人格或价值画像；
- 为所有用户同时推广商业、职业、关系和团队四套主定位；
- 在没有对应版本化加载、交互与降级证据时宣称宿主原生兼容。

## 14. 发布架构与声明扩展治理

v0.2.0 已将原 P0～P3 的协议工作合并为正式发布架构。后续版本可以扩展宿主与条件能力，但不能改变 Portable Core 的目的对齐、用户确认、授权分离、等待边界和证据诚实。

### 14.1 v0.2.0 已采用的架构

- 保留目的对齐、方法确认、唯一答案槽、判断、主现实闭环和四项反馈；
- 建立 Portable Decision Core 与 intent / consent / receipt / DecisionRecord schema；
- 建立 Evidence 与 Participation Policy；
- 建立 text、Claude Code 和 ChatGPT Adapter；
- 将单屏内联方法推荐、四类授权、Agent 总数公式、非递归、无投票综合、真人默认草稿和对话内快照纳入正式合同；
- current grader、fixtures、核心 UX 和增强 UX 统一维护 v0.2.0 合同；
- 冻结 v0.1 benchmark、legacy grader 和 discovery description 与当前合同隔离。

### 14.2 Claude Code 原生体验声明

Claude Code 中显式 `/think-it-through` 是当前正式入口。任何进一步的原生体验声明都应绑定版本化证据，包括：

1. R-align、R-method、A、B 的完整多轮记录；
2. single / multi 工具调用、方法 option description 与文本降级 trace；
3. B 四项反馈及 `native-note / follow-up-message / inline-text` 的实际表面；
4. 能力拒绝、失败和权限不足后的降级路径；
5. 与声明范围相符的核心 UX 评审。

这些证据用于扩大具体声明，不改变没有对应能力时仍可使用的纯文本基线。

### 14.3 Evidence、Participation 与真人参与治理

条件能力的版本化证据应覆盖：

1. 零调用基线与有界调研的路由差异；
2. 来源、日期、反证、停止条件、失败与认证降级；
3. 额外 Agent 的独立任务、总参与上限、最小上下文与非递归约束；
4. 计划、启动、完成、失败和实际总数回执；
5. 单 Agent 与协作增强在质量、等待、调用成本和用户控制上的比较；
6. 真人参与草稿与外部发送授权的分离。

扩大能力声明的前提是：不该升级时仍保持零调用或单 Agent；发生升级时可追溯任务、数据、权限、结果与失败；Agent 失败不阻塞 B；真人意愿不由模型代答。

### 14.4 跨宿主与复判治理

纯文本协议是跨宿主基线。新增宿主原生兼容或持久化声明时：

1. 用同一 conformance case 比较纯文本与目标宿主；
2. 先验证 Skill-only / 纯文本语义，再按实际能力扩展 MCP、持久化、服务端编排或自定义 UI；
3. 对每个宿主保留独立能力清单、授权、调用回执和降级证据；
4. 用粘贴或获授权读取的快照检查判断错误、执行偏差、资源错配和条件变化的区分；
5. 每个宿主单独维护兼容范围，不相互借用证据。

Adapter 的存在本身不扩大兼容声明；具体会话中的能力调用仍只由 observation、consent、trace 与 receipt 建立。

## 15. 评测与验收

### 15.1 保留现有三层证据

1. **发现性**：是否在正确请求加载，并避开负例；
2. **加载后行为**：是否遵守状态、控件、方法和授权合同；
3. **用户体验**：是否真的帮助用户形成更好的决定和行动。

### 15.2 v0.2.0 新增评测维度

在现有十维 UX rubric 上新增或独立评估：

- **调研适当性**：该查时查，不该查时不查；
- **证据质量**：来源、日期、反例、冲突与限制可见；
- **参与适当性**：单 Agent、多 Agent与真人路由合理；
- **成本透明**：用户知道时间、调用量、隐私和失败路径；
- **综合责任**：最终结论不是观点拼盘或投票；
- **跨宿主保真**：控件和能力变化不破坏核心语义；
- **解决方案完整性**：有方向、条件、反转信号和主下一步；
- **复判质量**：真实结果能更新判断而非合理化旧选择。

### 15.3 必测场景

#### 调研路由

- 公开、时效性市场事实会反转判断 → 应先调研；
- 用户价值未知 → 不调研，问用户；
- 搜索只增加背景 → 不调研；
- 调研失败或来源冲突 → 条件化判断并降级；
- 需要联系客户 → 单独外部行动授权。

#### 多 Agent

- 两个独立市场可并行 → 可建议多 Agent；
- 同一问题重复分析 → 保持单 Agent；
- 用户上限低于建议数 → 严格遵守用户上限；
- Agent 失败 → 主 Agent 继续；
- 多数 Agent 同意但无独立证据 → 不提高置信度；
- 成本超过事项价值 → 不启用。

#### 真人多人

- 团队权责冲突 → 邀请真实决策人而非继续生成 Agent；
- 客户意愿 → 转为行为证据；
- 专业高风险 → 整理咨询重点；
- 未授权发送 → 只生成材料。

#### 跨宿主

- Claude Code 有原生控件 → 必须有真实工具回执；
- ChatGPT 只有文本 → 用紧邻的编号说明保留正式名称、推荐状态、当前价值、候选范围、最终组合提交和自由调整；
- 自定义 UI 加载失败 → 只降级一次，且不省略方法确认；
- 搜索 provider 不存在 → 不假装已联网；
- 子 Agent 不可用 → 单 Agent 路径通过。

### 15.4 产品成功指标

不要以 Agent 数、工具调用数或报告长度为北极星。建议观察：

#### 激活

- 用户能否在一次会话中说清真实目的和当前决定；
- 显式调用后完成到正式判断的比例；
- 在方法确认、Evidence Gate 或协作提示处的流失。

#### 决策质量代理指标

- 用户是否认为系统准确理解其目的；
- 用户是否理解每个推荐角度此刻为何有用，并知道自己最终确认了哪些方法；
- 用户是否能复述判断为何成立、何时会改变；
- 唯一问题是否真的改变了排序、承诺或实验设计；
- 调研有多少次实际改变判断，而不是只增加篇幅；
- 多 Agent 有多少次发现单 Agent 未发现的关键反证或来源冲突。

#### 行动与复判

- 现实实验采用率；
- 高成本全面投入被改为小步验证的比例；
- 复判到期后回访率；
- 继续、调整、暂停、停止的分布，而不是只看“推进率”；
- 决策快照被再次使用的比例。

#### 信任与控制

- 目的误判后成功纠正率；
- 未授权能力、数据或外部行动发生次数必须为零；
- 用户是否理解多 Agent 用途、实际数量和上限；
- 来源错误、虚构调用和跨宿主能力误报次数必须为零。

### 15.5 反转条件

出现以下证据时应调整方案：

- 如果真实用户很少需要前置调研，且它主要增加流失和延迟，则恢复“先判断、后验证”为唯一默认；
- 如果多 Agent 对判断质量没有稳定增益却显著增加成本，则保持关闭或删除；
- 如果 v0.1.5 的控件前完整说明造成重复扫描或流失，优先改为“正式方法名 + 推荐状态 + 当前价值内联选项 + 一步确认/调整”；若内联导致描述难读或选择质量下降，则保留紧邻说明，但方法透明、唯一最终组合提交和用户调整权不得取消；
- 如果决策快照很少被复用，则保持对话内、按需生成，不建设持久化服务；
- 如果 ChatGPT 或其他宿主发布稳定、通用的结构化交互与子 Agent 标准，则简化 adapter；
- 如果商业 ICP 的激活和复判价值不成立，再扩大主定位，而不是一开始同时服务所有人群；
- 如果 `grilling` 式规格澄清比本产品更符合某类触发，应明确转介，不扩大 Think It Through 边界。

## 17. 风险与防护

| 风险 | 可能后果 | 防护 |
| --- | --- | --- |
| 功能膨胀 | 从克制决策 Skill 变成复杂平台 | 以决策增益为唯一新增门槛，P0 先验证现有核心 |
| 调研拖延 | 用户永远等更多信息 | Evidence Gate、停止条件、边际价值和失败降级 |
| 多 Agent 权威幻觉 | 一致意见被当作事实 | 独立证据、来源去重、禁止投票、主 Agent 综合 |
| 用户成本不透明 | 延迟、token 或付费超预期 | 启用前说明任务、数量、上限和影响 |
| 隐私扩散 | 同一私有上下文复制给多个 Agent | 最小数据范围、按 Agent 任务裁剪、数据授权分离 |
| 真人被模型替代 | 价值、承诺和责任被伪造 | 真人参与路由，Agent 不代答真实意愿 |
| 跨宿主误报 | 文档宣称能力但当前 surface 不支持 | capability negotiation、receipt 和逐宿主版本化证据 |
| 流程压过结果 | 用户学会状态机却没得到方向 | 用户前台只见必要选择和最终解决方案 |
| 长期记忆侵入 | 隐私和错误画像累积 | 默认不持久化，用户可见、可删，不存隐藏推理 |
| 与 grilling 边界含混 | 两个 Skill 重复或互相抢触发 | decision readiness 与 specification completeness 明确路由 |

## 18. 最终产品原则

1. **解决方案优先，但不越过用户价值权。**
2. **单 Agent 默认，但不是产品上限。**
3. **Agent 上限由用户控制，实际数量由独立任务决定。**
4. **该调研时先调研，不该调研时零调用最好。**
5. **可查事实由系统找，价值、底线和承诺由真实的人决定。**
6. **多 Agent 提供材料，主 Agent 承担综合，证据而非投票决定置信度。**
7. **真人多人解决分布式权责，不能由更多模型替代。**
8. **方法由系统最小路由，并优先以“正式名称 + 推荐状态 + 当前价值”的单屏选择和最终确认对用户透明。**
9. **一个关键答案和一个主证据闭环继续保持产品克制。**
10. **跨平台以语义和降级为核心，不以专有控件为核心。**
11. **每个判断都应留下可复判条件，而不是只留下漂亮答案。**
12. **停止、暂停和转向与推进同样是成功结果。**
13. **不以框架、角色、Agent、调用或报告数量证明价值。**
