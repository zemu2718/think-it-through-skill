# Think It Through 立项价值反证优化方案

> 文档状态：非规范性优化提案
>
> 创建日期：2026-09-02
>
> 适用对象：Think It Through 后续合同版本
>
> 当前基线：v0.3.0
>
> 正式依据：实施后仍以 [`REQUIREMENTS.md`](../REQUIREMENTS.md) 为唯一行为、安全与验收合同

## 1. 文档目的

本方案将一次真实项目教训转化为 Think It Through 可重复执行、可验证、可降级的立项保护机制。

它要解决的核心问题是：当用户准备启动新产品、重大功能、核心定位调整或高成本基础设施建设时，Skill 不能直接帮助用户把既定方案设计得更完整，而应先判断这项投入是否有必要发生。

优化后的 Skill 应能够：

1. 把用户提出的产品形态降级为候选解法，而不是直接视为真实问题；
2. 分开验证问题存在、问题强度、方案适配和替代生态；
3. 从用户结果出发搜索直接竞品、相邻赛道、平台原生能力和非同形替代；
4. 发现并核验名称不同但用户结果高度重合的现有方案；
5. 要求先用真实任务试用最强现实替代；
6. 在必要且获授权时引入认知独立的反方审查；
7. 在证据不足时限制投入，而不是把未知解释成支持自研；
8. 当定位、用户、场景或替代生态实质变化时，使旧结论失效并触发复查。

本方案不保证一次搜索必然发现某个指定产品。它通过两道防线降低重大误投：

- 第一层提高发现强替代的概率；
- 第二层在替代生态仍不充分时禁止无条件扩大投入。

## 2. 问题定义

### 2.1 要避免的失败模式

需要系统降低以下风险：

- 按计划采用的实现形式搜索，而不是按用户要获得的结果搜索；
- 只检查直接同形竞品，遗漏相邻赛道和非同形替代；
- 只看项目默认分支或首页，遗漏近期 Release、活跃分支和正在形成的能力；
- 把架构完整、概念严谨或低频功能差异当成市场机会；
- 没有实际试用最强替代，就根据文档宣称现有方案不够；
- 已倾向立项后，只寻找支持自研的材料；
- 过早进入领域模型、后端、数据库、跨平台和正式 UI 设计；
- 因沉没成本继续投入；
- 产品定位变化后继续沿用旧调研结论；
- 搜索没有发现结果时，把“未发现”写成“不存在”。

### 2.2 核心设计判断

新增能力不应成为一张可选方法卡，也不应新增一个独立 `Veto Gate` 状态。

原因是：

- 实现形式去锚属于 Decision Core 的基本分析纪律；
- 外部替代搜索属于 Evidence Gate；
- 独立反方属于 Participation Gate；
- 允许投入的范围与停止条件属于 B；
- 这些保障不应因用户未选择某张方法卡而消失；
- 新状态会破坏现有唯一流程，并与 `hold / pause / stop` 重复。

因此，本方案采用“增强现有层、保持现有状态机”的方式落地。

## 3. 核心产品纪律

后续合同应把以下原则收敛为一条可验收的行为约束：

> 当决定要求投入大量时间、资金、组织承诺或基础设施时，Think It Through 应先把用户提出的产品或功能形态视为候选解法，分别验证真实问题、问题强度、方案适配和替代生态。若“必须自研”仍依赖未经核实的外部事实，则最多建议采用、集成、有限验证或暂停，并明确当前承诺上限。只有最强现实替代经过真实使用仍无法解决用户在意的核心问题，自研才获得继续举证的资格。

由此派生四条不变量：

1. **实现形式不是问题定义**：用户说“做一个应用”“加一个 AI 功能”或“建设一个平台”，只能形成候选解法。
2. **未知不是支持证据**：未搜索、未授权、未试用、调用失败和来源不足都必须保留为未知。
3. **自研承担举证责任**：若成本更低的现实路径尚未被合理排除，不应无条件进入独立自研。
4. **承诺必须与证据匹配**：证据越弱，允许的投入越小、越可撤回。

## 4. 适用范围与触发条件

### 4.1 适用决定

立项价值反证适用于：

- 新产品立项；
- 重大功能方向；
- 核心定位调整；
- 从验证阶段进入正式开发；
- 准备建设新后端、数据库、平台或其他昂贵基础设施；
- 从局部工具扩展成平台或生态；
- 已有项目继续、收缩、暂停或停止的复判；
- 出现重要竞品、平台原生能力或替代技术后的继续投入判断。

### 4.2 不适用或轻量处理

以下任务不应被强制扩展成完整市场调研：

- 已决定且低风险的执行；
- 小型、可快速撤回的个人实验；
- 单纯事实查询；
- 固定范围的技术实现或代码审查；
- 紧急处置；
- 外部事实不会改变决定的纯偏好选择。

即使适用，也不代表固定执行完整行业报告。只有会改变路径排序、是否继续或投入边界的未知，才进入 Gate。

### 4.3 可靠入口边界

当前可靠入口仍是显式调用：

```text
/think-it-through
```

后续可以优化 Skill description，提升自然语言发现概率，但在真实 runtime 证据建立前，不得宣称用户只要表达立项意图就一定会自动加载。

建议形成使用纪律：

> 每次新产品、重大功能或核心定位调整，在规划和编码前显式调用 `/think-it-through`。

## 6. 各阶段行为设计

### 6.1 R-align：实现形式去锚

当用户说“我要做 X”时，内部分析应区分：

- 目标用户；
- 核心场景；
- 期望结果；
- 当前做法；
- 具体失败；
- 发生频率与成本；
- 真实约束；
- 用户提出的候选解法。

用户提出的产品名称、功能列表、技术架构或交互形态不能自动成为正式问题定义。

R-align 仍然遵守当前交互合同：

- 不调用搜索、文件、Agent 或真人参与；
- 不把澄清变成完整问卷；
- 只对齐当前最大的一个未知；
- 可并存目的先合并，不默认排序；
- 只有真实排他约束会改变决定时才继续澄清。

### 6.2 R-method：方法与能力保持分离

方法选择继续服务于认知视角，不承担外部执行能力。

以下内容不得进入方法 registry：

- 市场调研；
- 竞品扫描；
- 活跃项目核验；
- build-vs-buy；
- 独立反方 Agent；
- 否决门；
- 真人参与；
- 持久化或宿主适配。

双向钢人可以比较已形成的方向，但不能替代候选生态发现；失败预演可以发现失败机制，但不能替代问题验证和替代方案试用。

### 6.3 A：选择一个决定敏感问题

A 仍然只有一个答案槽，并在提问后等待。

立项场景中，优先考虑的问题类型包括：

- 如果已有方案满足核心结果，仍必须自研的高频失败是什么？
- 当前哪项事实最可能让用户改为采用、集成或停止？
- 用户是否实际为这个问题付出持续成本？
- 剩余差异是否会改变迁移、持续使用或付费行为？

A 不能提前请求搜索，也不能把多个独立验证问题塞入一个答案槽。

### 6.4 Gate-routing：只调查会改变决定的未知

用户回答 A 后，判断：

- 未知是否可由用户本人回答；
- 是否属于外部可验证事实；
- 是否需要认知独立的参与；
- 是否应交给现实试用而不是继续分析；
- 获取价值是否高于时间、费用和隐私成本。

当判断依赖以下命题时，应优先考虑 Evidence Gate：

- “市场上没有可采用的方案”；
- “只有自研能够满足”；
- “平台原生能力不支持”；
- “竞品缺少某项核心能力”；
- “某个开源项目已经停止维护”；
- “剩余差异足以形成真实用户价值”。

如果搜索不可用、状态为 `unknown`、授权被拒绝或调用失败，记录后继续条件化 B，不阻塞流程。

## 7. 四层证据模型

立项判断应明确区分以下证据：

| 层级 | 回答的问题 | 合格证据示例 | 不能替代它的内容 |
| --- | --- | --- | --- |
| 问题存在 | 真实用户是否遇到问题 | 真实任务失败、用户行为、访谈原话、支持请求 | 市场趋势、产品概念、竞品数量 |
| 问题强度 | 问题是否高频或高成本 | 重复劳动、金钱损失、主动寻找方案、迁移意愿 | 一次抱怨、内部想象、未来可能性 |
| 方案适配 | 候选方案能否解决问题 | 同一真实任务试用、完成率、稳定失败记录 | 功能列表、架构完整度、UI 设计 |
| 替代生态 | 是否有更低成本的现实路径 | 直接采用、组合工具、平台能力、流程替代及成本 | “暂未发现”、单一关键词搜索 |

判断纪律：

- 问题存在不自动证明问题足够强；
- 问题很强不自动证明指定方案适配；
- 竞品存在不自动证明用户需求；
- 竞品缺少功能不自动证明差异有价值；
- 未知不得被折算为支持自研。

## 8. 用户结果优先的替代生态搜索

### 8.1 两遍搜索

#### 第一遍：问题与用户结果语言

优先从以下维度生成查询：

- 用户是谁；
- 要完成什么任务；
- 要获得什么结果；
- 当前在哪里失败；
- 有哪些现实约束；
- 用户如何用自然语言表达；
- 中英文或领域内其他常见表达。

#### 第二遍：产品与实现语言

再补查：

- 用户提出的产品类别；
- 技术实现词；
- 行业术语；
- 已发现竞品使用的自定义术语；
- 相关平台和接入环境。

Evidence record 应能够说明两类搜索边界，避免一次仅使用同形产品关键词的搜索被误写成完整替代调查。

### 8.2 替代候选空间

候选池应按决定相关性检查以下路径，而不是机械要求每次完整输出：

1. 不做或维持现状；
2. 人工或流程调整；
3. 直接竞品；
4. 相邻类别；
5. 非同形产品或服务；
6. 平台原生能力；
7. 活跃开源项目；
8. 商业产品；
9. 多工具组合；
10. 插件、脚本或薄集成；
11. 局部补充；
12. 独立自研。

若结论为自研，应能解释成本更低的主要现实路径为什么不足。

### 8.3 高相关项目的完整核验

对最可能改变决定的高相关项目，不能只看首页或默认分支。按可获得性检查：

- 当前定位和目标用户；
- 默认分支与活跃非默认分支；
- Releases、CHANGELOG 和 Roadmap；
- 最近活动、Issues 和 Pull Requests；
- 已实现、Beta 和规划能力；
- 安装与部署方式；
- 维护者或供应商状态；
- License 和商业限制；
- 数据、隐私、权限和模型调用边界；
- 采用信号；
- 集成、迁移、维护和退出成本。

无法获得的信息保留为空白，不用推测填充。

### 8.4 来源和停止条件

调研前说明：

- 当前决定；
- 单一证据问题；
- 搜索范围；
- 来源类型；
- provider 和拟发送数据；
- 时间或费用边界；
- 停止条件；
- 失败后的降级方式。

停止条件应与决定相关，例如：

> 已发现足以改变当前路径排序的强替代，并完成关键来源核验；继续扩大搜索预计不会改变“先试用而不是自研”的决定。

不以固定报告长度、搜索次数或 `maxTurns` 代替语义停止条件。

## 9. 最强替代试用

### 9.1 试用义务

对于重大投入，公开资料只能用于建立候选池，不能单独证明现有方案不适用。

应选择足以代表最强现实替代集合的方案，使用同一组真实任务进行试用。默认可以考虑三个强候选，但不把固定数量写成所有场景的硬合同。

尚未试用的强替代必须保留为关键未知。

### 9.2 统一试用记录

每次试用至少记录：

```text
候选方案：
检查日期与版本：
代表的替代路径：
真实任务：
安装或部署成本：
首次成功时间：
核心流程完成情况：
稳定性与失败点：
数据和权限边界：
集成与迁移成本：
维护与退出成本：
是否满足核心用户结果：
哪些缺口可由配置、插件或薄集成解决：
哪些事实仍未知：
对当前判断的影响：
```

### 9.3 试用后的路径

```text
满足核心用户结果
→ 采用现有方案

核心结果基本满足，存在局部缺口
→ 薄集成或局部补充

关键缺口尚未证明高频或重要
→ 有限验证或暂停

真实、高频、高成本的核心缺口稳定存在，且不能低成本补齐
→ 自研获得继续举证资格
```

“获得继续举证资格”不等于自动批准完整开发，仍需评估成本、收益、能力和停止条件。

## 10. 独立反方机制

### 10.1 进入条件

默认保持单 Agent。只有在以下条件成立时，才建议额外参与：

- 决定高投入、低可逆；
- 主判断高度依赖候选空间是否完整；
- 存在不重复、可验证、可停止的独立反证任务；
- 预期增量高于参与成本；
- 用户对 `participation_delegation` 明确授权；
- 若还需搜索，则另有 `capability_call` 授权。

用户参与总上限仍是硬上限，不是使用目标。

### 10.2 认知独立性

独立反方应尽量只接收：

- 用户目标；
- 已确认事实；
- 决策标准；
- 必要约束；
- 明确的反证任务和停止条件。

尽量不接收：

- 主 Agent 的最终判断；
- “为什么我们与众不同”的方向性材料；
- 已经排好顺序的候选结论；
- 与任务无关的完整对话。

反方返回：

- 最强否决理由；
- 最强现实替代或组合；
- 主分析可能遗漏的类别；
- 支持和反对证据；
- 信息冲突与空白；
- 哪项证据会改变结论；
- 失败、超时或无法完成的部分。

### 10.3 失败降级

反方任务失败、超时、来源不足或未获授权时：

- 不把“未发现反证”当成支持；
- 降低判断置信度；
- 收紧承诺上限；
- 基于已有信息进入条件化 B；
- 不阻塞用户结束流程。

主 Agent 继续负责去重、呈现冲突和综合，不进行多数投票。

## 11. B：判断、承诺上限与 no-go

### 11.1 允许的判断方向

立项场景中的最终判断可以是：

- **采用**：直接使用现有方案；
- **集成**：围绕现有方案做插件、脚本或薄适配；
- **有限验证**：只验证一个最关键假设，不正式立项；
- **有条件自研**：条件成立后进入受限范围；
- **暂停**：等待决定敏感证据；
- **停止**：现有路径已不值得继续。

禁止以“先做着看”代替正式判断和投入边界。

### 11.2 B 的立项增量

在不破坏现有“一个综合判断、一个主现实闭环、一个决策快照和四项反馈”的前提下，B 应无损表达：

- 当前判断；
- 最强现实替代；
- 四层证据分别处于什么状态；
- 关键未知；
- 当前允许的最大承诺；
- 升级投入必须满足的条件；
- 当前 no-go 条件；
- 触发暂停、停止或复查的信号；
- 下一项可撤回的主现实证据闭环。

### 11.3 承诺级别

可以先在参考层使用以下语义，不立即固化为 schema enum：

```text
L0：只讨论，不投入
L1：收集用户答案或公开证据
L2：安装、试用或手工验证
L3：小范围原型或薄集成
L4：受限开发
L5：正式产品与基础设施投入
```

纪律是：当前证据只能支持相应或更低级别的承诺。

示例：最强替代尚未试用时，最多进入 L2，不能直接进入 L4 或 L5。

### 11.4 no-go 条件

以下情况默认不得扩大不可逆投入：

- 问题存在或强度尚未得到现实证据支持；
- 最强现实替代尚未合理核验或试用；
- 剩余差异主要位于架构、概念或低频边缘能力；
- 用户是否在意该差异仍未知；
- 缺口可能通过脚本、插件或薄集成解决；
- 需要先建设大量基础设施才能验证需求；
- 独立反证的关键任务失败，却没有其他证据补足；
- 继续投入的主要理由是沉没成本；
- 无法说明用户为什么不用现有方案。

这里不使用“覆盖 80%”等伪精确阈值。判断应围绕核心用户结果和真实行为，而不是功能数量。

## 12. 重新调研触发条件

以下变化应使旧结论进入待复核状态：

1. 核心定位变化；
2. 目标用户变化；
3. 核心场景或期望结果变化；
4. 从局部工具扩展为平台；
5. 准备建设新的高成本基础设施；
6. 从验证阶段进入正式开发或公开发布；
7. 出现高相关新产品、重大 Release 或平台原生能力；
8. 原有关键差异被现有方案覆盖；
9. 原结论依赖的版本、维护状态、价格、License 或部署边界发生变化；
10. 到达上次决策记录定义的复查日期或事件。

不把统一的“每 4～6 周”写成全局硬规则。各领域根据变化速度设置日期或事件触发器。

每次复查至少回答：

```text
什么事实发生了变化？
旧判断依赖的哪些前提已失效？
当前最强现实替代是谁？
原有差异是否仍存在？
用户是否已经用行为证明这些差异重要？
当前投入上限是否仍然合理？
```

## 13. 对市场调研 Agent 模板的取舍

通用市场调研 Agent 的以下能力值得吸收：

- 先界定研究对象、时间、地域和决策场景；
- 区分事实、估计、假设和待验证内容；
- 关键结论进行多来源交叉验证；
- 记录来源和时间；
- 数据不可得时保留未知；
- 使用结构化比较帮助阅读。

以下设计不直接照搬：

- 默认执行完整 TAM / SAM / SOM、趋势、画像、SWOT、五力和 GTM；
- 以寻找空白市场和差异化定位为默认目标；
- 始终自动调用 WebSearch 或 WebFetch；
- 仅用“直接与间接竞争者”概括替代生态；
- 用固定 Phase 和 `maxTurns` 代替决定敏感问题与停止条件；
- 仅根据公开资料形成“进入市场”建议；
- 缺少最强替代试用、独立反方和承诺上限。

Think It Through 应吸收其研究纪律，但保持“先允许项目被否决”的决策目标。

## 14. 示例：一人公司 Agent 团队

### 14.1 用户输入

```text
我想给一人公司组建一支有组织、有记忆、会积累经验的 Agent 团队。
```

### 14.2 R-align 结果

把真实目的表达为：

> 让一人公司能够长期使用一支有明确分工、共享或隔离记忆、能够沉淀经验并持续协作的 Agent 团队。

“开发一个独立产品”只是一种候选解法。

### 14.3 Evidence Gate 的证据问题

```text
是否已经存在能够完成这个核心用户结果、且采用成本显著低于独立自研的产品、平台能力或工具组合？
```

经授权后，先使用用户结果语言搜索，再扩展到：

- Agent Memory；
- Agent Knowledge Hub；
- Multi-Agent Team；
- Agent Workspace；
- Agent Loadout；
- Agent Control Plane；
- AI Employee / AI Company；
- Claude Code、Codex、OpenClaw 等平台或客户端能力；
- 组合与薄集成路径。

高相关候选可能包括：

```text
https://github.com/TencentCloud/TencentDB-Agent-Memory
```

发现该项目后，应核验其当前版本、活跃开发面、Team / Agent / Memory / Skill 等实际能力、接入方式、数据权限和部署成本，而不是仅依据名称或首页分类。

### 14.4 合理的投入上限

如果该项目及其他强替代尚未完成真实任务试用：

```text
允许：部署、试用、记录核心失败点，或制作极薄的验证适配。
不允许：建设重复的 Memory、Team、ACL、知识基础设施、完整后端和正式产品架构。
```

### 14.5 路径判断

```text
现有方案满足核心结果
→ 采用或停止重复建设

现有方案有局部且重要的缺口
→ 薄集成或局部补充

缺口是否高频、重要仍未知
→ 有限验证

核心缺口经真实任务证明稳定存在，且不能低成本补齐
→ 极度收缩范围后考虑自研
```

即使一次搜索未发现该仓库，也不能据此批准重大投入；“替代生态仍未知”应继续限制承诺。

## 15. 与现有状态机和授权模型的兼容

### 15.1 保持不变

唯一状态流保持：

```text
空状态
→ R-align
→ R-method
→ A
→ Gate-routing
→（必要且获授权时）Evidence Gate / Participation Gate
→ B
→ 反馈 / 结束 / 新一轮 R
```

保持以下现有约束：

- R 和 A 零外部调用；
- A 回答后才路由 Gate；
- Gate 是条件能力，不是固定阶段；
- 能力不可用、未知、拒绝或失败时进入条件化 B；
- 默认单 Agent；
- 多 Agent 需要增量价值、数量上限和独立授权；
- 主 Agent 综合，不投票；
- 四类授权互不继承；
- 默认不持久化；
- B 保持一个判断、一个主现实闭环、一个快照和四项反馈。

### 15.2 明确禁止的实现

- 不在 pre-entry 执行完整产品发现；
- 不在 R 或 A 搜索竞品；
- 不把替代扫描放入 R-method；
- 不固定启动反方 Agent；
- 不新增 `Veto Gate`；
- 不把问题验证、替代扫描、渠道验证包装成一个现实实验；
- 不用一次授权同时继承搜索、Agent、私有数据或外部行动权限；
- 不把一次安装、搜索或静态 fixture 描述为真实 runtime 已通过。

## 16. 信息记录与 Schema 策略

### 16.1 第一阶段不急于修改 Schema

现有 intent、consent 和 receipt 足以承载首轮行为改进。优先在文本合同、policy、reference、fixture 和 grader 中验证语义是否稳定。

Evidence record 和 DecisionRecord 先以现有字段无损记录：

- 问题定义；
- 四层证据状态；
- 最强现实替代；
- 主要候选路径及排除理由；
- 未验证的关键替代；
- 独立反证结果；
- 当前承诺上限；
- no-go 和升级条件；
- 复查触发器。

### 16.2 后续 Schema 进入条件

只有在 fixtures、grader 和真实 runtime episode 证明字段稳定、通用且需要机器审计后，才考虑版本化修改 `decision-record.schema.json`。

不把完整竞品账本、固定渠道、固定候选数量或市场专用框架固化进通用 schema。

## 18. 评测方案

### 18.1 确定性合同场景

至少新增以下 current fixtures：

1. **产品形态去锚**：用户直接要求开发 AI 产品，合格行为先重构用户结果；
2. **证据分层**：区分问题存在、强度、方案适配和替代生态；
3. **搜索偏置**：只按产品类别搜索失败，问题语言优先通过；
4. **非同形替代**：发现平台能力、流程方案或工具组合；
5. **活跃项目**：默认分支不足，近期活动或活跃分支改变判断；
6. **采用优先**：自研不能成为未经比较的默认选项；
7. **最强替代试用**：仅阅读 README 不足以排除强替代；
8. **反方独立性**：反方不应只复述主判断；
9. **反方失败降级**：任务失败后无条件 `proceed` 应失败；
10. **承诺上限**：证据不足时扩大不可逆投入应失败；
11. **重新调研**：定位变化后沿用旧结论应失败；
12. **沉没成本**：已有投入不能成为继续开发的主理由。

### 18.2 TencentDB 发现案例

建立两层测试，避免硬编码单一仓库。

#### 合同级候选识别

提供模拟候选集合，其中包括：

- 名称属于 Agent Memory 但用户结果高度重合的项目；
- 直接叫 Agent Team 的项目；
- 平台原生能力；
- 工具组合；
- 低相关项目。

验证 Skill 能否将名称不同但目标重合的项目提升为强候选，并限制重大投入。

#### 真实运行发现

测试提示不出现 TencentDB、TencentCloud 或仓库名称，只描述：

```text
给一人公司组建一支有组织、有记忆、会积累经验的 Agent 团队。
```

在显式调用、工具可用和取得授权的条件下，检查是否：

1. 先按用户结果搜索；
2. 扩展到 Agent Memory、Knowledge Hub、Agent Team 等相邻类别；
3. 发现并核验 `TencentCloud/TencentDB-Agent-Memory` 或同等级强替代；
4. 查看当前版本、活动和关键能力，而不是仅看名称；
5. 将其列入最强替代；
6. 在实际试用前拒绝批准重大自研。

这项结果必须绑定源码 revision、runtime/version、日期、provider、搜索工具、授权和 receipt。静态 fixture 不能证明真实发现能力。

### 18.3 Grader 边界

Grader 可机械检查：

- 阶段顺序；
- R/A 零外部调用；
- Gate 授权；
- 两类查询边界是否记录；
- 候选类别是否存在结构表示；
- 来源和日期；
- 反方 payload 是否最小且不含主结论；
- B 是否表达关键未知、承诺上限和 no-go；
- 失败后是否降级。

Grader 不能仅靠关键词证明：

- 候选是否真正最强；
- 搜索是否足够完整；
- 用户是否真的在意差异；
- 反方是否具有真实认知独立性；
- 某次 runtime 是否确实发现具体项目；
- 真实 UX 是否良好。

这些仍需语义 rubric、人工审阅和绑定版本的真实 runtime episode。

### 18.4 对照评测

实施时保留 v0.3.0 快照作为基线，对相同提示运行：

- 旧 Skill；
- 新 Skill；
- 必要时无 Skill 基线。

比较：

- 是否更早解除方案锚定；
- 是否发现更多非同形强替代；
- 是否减少无条件自研建议；
- 是否保持一个问题和有界 Gate；
- 是否避免输出过重的完整市场报告；
- 是否增加不必要轮次或搜索成本。

评测结果应通过 reviewer 供人工比较，不能只看自动分数。

## 19. 分阶段实施计划

### 阶段 0：建立失败基线

目标：先证明现有 v0.3.0 在哪些场景会遗漏或过早推进。

产出：

- 代表性提示集；
- v0.3.0 Skill 快照；
- 旧版输出；
- 结构 assertion 和语义 rubric；
- 基线评测状态。

停止条件：已能稳定区分“当前能力已覆盖”和“本方案新增能力”。

### 阶段 1：核心分析与 Evidence Policy

目标：先解决实现形式去锚、四层证据、两遍搜索和替代生态。

优先修改：

- `REQUIREMENTS.md`；
- `SKILL.md`；
- `core/protocol.md`；
- `references/core-analysis.md`；
- `policies/evidence-routing.md`；
- 新增 `references/project-viability.md`。

暂不修改 schema，不固定启动多 Agent。

停止条件：确定性 fixtures 能约束基本行为，且没有破坏 R/A/Gate/B。

### 阶段 2：最强替代试用、反方与承诺上限

目标：让“发现替代”真正改变投入边界。

修改：

- Participation Policy；
- external validation；
- B 合同与 DecisionRecord 映射；
- grader 和失败 fixtures。

停止条件：未试用强替代、反方失败或证据不足时，输出不会无条件扩大投入。

### 阶段 3：真实运行与发现能力验证

目标：验证真实 runtime 是否能按用户结果发现非同形替代，并正确协商授权。

执行：

- 显式 Skill 调用；
- 固定 runtime 和 provider；
- 公开搜索授权；
- TencentDB 案例与其他未知案例；
- 脱敏、receipt 和人工审阅。

停止条件：形成绑定准确版本的候选 evidence；未运行或失败项保持真实状态。

### 阶段 4：触发 description 优化

目标：在行为稳定后提升相关立项意图的自然语言发现概率。

执行：

- 设计 should-trigger 与 should-not-trigger 提示；
- 覆盖新产品、重大功能、定位调整和继续加码；
- 覆盖低风险执行、事实查询和普通技术任务等近似负例；
- 训练集与 holdout 分离；
- 避免继续针对冻结 v0.1 holdout 调优。

即使 description 得分提升，公开入口仍按真实证据声明。

### 阶段 5：版本化、分发与公开说明

目标：完成合同同步、全量验证和分发复验。

执行：

- 同步版本链路；
- 更新公开文档中真正发生变化的部分；
- 同步本地安装副本；
- 运行完整单元测试、validator、资产检查和空白检查；
- 在新的空目录构建 `.skill` 并复验；
- 只有 Git tag、Release 和 asset 真实创建后才声明。

## 20. 验收标准

### 20.1 行为验收

优化后应满足：

- 用户提出实现形式时，Skill 能把它还原为用户结果与候选解法；
- 立项结论明确区分四层证据；
- “没有替代”依赖外部事实时会在 A 后进入有授权的 Evidence Gate；
- 搜索先使用问题与用户结果语言，再补查方案语言；
- 候选空间包括直接和非同形现实路径；
- 高相关活跃项目不会只凭首页被排除；
- 最强替代未试用时不会无条件批准重大自研；
- 独立反方只在有增量且获授权时启用；
- 反方或搜索失败不会被解释成支持证据；
- B 给出与证据匹配的承诺上限和 no-go；
- 定位或替代生态变化能触发重新验证；
- 不把每次立项都扩展成完整行业研究报告。

### 20.2 安全与授权验收

- R 和 A 不调用外部能力；
- 搜索、Agent、私有数据和外部行动授权互不继承；
- 未授权、拒绝和失败产生诚实记录；
- 不读取无关私有数据；
- 试用涉及安装、执行、账号或外部行动时按具体风险另行确认；
- 默认不把调研账本或 DecisionRecord 写入文件或远端；
- 不持久化隐藏思维链。

### 20.3 证据验收

- 静态合同、fixtures 和 grader 只声明其能证明的层级；
- 真实搜索发现绑定 runtime、provider、日期、授权和 receipt；
- 未运行项保持 `not_run`；
- 不用单个 TencentDB 案例证明所有市场都不会漏检；
- 不宣称自然语言自动加载已经可靠，除非对应证据真实建立。

## 21. 风险与控制

| 风险 | 表现 | 控制方式 |
| --- | --- | --- |
| 过度调研 | 每个小决定都生成长报告 | 只调查决定敏感问题，使用进入和停止条件 |
| 过度否决 | 新项目永远无法开始 | 承诺分级，允许低成本、可撤回的有限验证 |
| 搜索清单化 | 机械扫渠道但仍漏语义 | 用户结果优先、候选类别与搜索词动态生成 |
| 反方仪式化 | 额外 Agent 只是复述 | 最小上下文、去锚、独立任务和失败降级 |
| 虚假精确 | 用 80%、三家、固定周期冒充判断 | 默认值留在参考层，核心合同围绕用户结果 |
| Schema 过早固化 | 市场专用字段污染通用协议 | 先以运行证据验证字段稳定性 |
| 发现能力过度承诺 | 一次找到 TencentDB 就宣称不会漏检 | 真实运行分层声明，加承诺上限作为第二防线 |
| 状态机膨胀 | 新增 Veto 阶段破坏现有合同 | 增强 core、policy 和 B，不新增状态 |
| 旧结论惯性 | 定位变化仍沿用旧调研 | 复查触发器和 DecisionRecord 反证条件 |

## 22. 完成定义

本优化只有同时满足以下条件才算完成：

1. 新行为进入 `REQUIREMENTS.md`，且没有形成第二份正式合同；
2. SKILL、core、policies、references 和 adapters 语义一致；
3. current fixtures 和 grader 覆盖主要通过与失败边界；
4. R/A/Gate/B 状态、授权和降级语义未被破坏；
5. 新增运行时 reference 已进入分发 manifest；
6. 完整测试、validator、分发复验和 `git diff --check` 通过；
7. 本地安装副本与唯一维护源一致；
8. 真实 runtime 结果按实际状态记录，不由静态测试冒充；
9. 双语公开文档只同步普通用户真正需要知道的变化；
10. 至少一次人工评审确认：新版本提高了立项保护能力，同时没有把 Skill 变成固定市场报告生成器。

## 23. 推荐实施顺序

建议按以下顺序推进：

```text
确认本提案边界
→ 建立 v0.3.0 失败基线和 eval
→ 修改正式合同与核心分析
→ 增强 Evidence Policy
→ 增加 project-viability 参考
→ 增强 Participation Policy 与 B 承诺上限
→ 更新 grader、fixtures 和 validator
→ 对照评测与人工审阅
→ 真实 runtime 发现测试
→ description 优化
→ 全量验证、版本化和分发
```

先建立 eval，再修改合同，可以避免根据单一 Bandi 案例过拟合；先稳定行为，再优化 description，可以避免提升了触发率却触发一个尚未可靠的流程。

## 24. 最终目标

真正吸取这次教训，不是让 Skill 输出更长的竞品报告，而是让它在重大投入前稳定形成下面的判断顺序：

```text
先确认真实问题
→ 再确认问题是否足够重要
→ 再寻找并试用最强现实替代
→ 再判断能否采用、组合或薄集成
→ 证据不足时限制投入
→ 只有核心缺口经现实证明后才考虑自研
```

优化成功的标志不是“每次都能找到某一个指定仓库”，而是：

> 即使搜索偶尔漏项，只要问题价值、替代生态或自研必要性尚未得到充分证明，Skill 就不会轻易建议用户进入重大、难以撤回的投入。
