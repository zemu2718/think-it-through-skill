# Participation Policy：Agent 上限与真人参与

## 目标

Participation Policy 决定谁应参与以及为什么参与。默认使用当前主 Agent；只有独立参与能带来明确决策增量时才升级。多 Agent 和真人参与是能力路由，不是方法卡，也不能用角色数量、投票或模型一致性制造权威。正式 Participation Gate 只在 A 的用户答案之后路由；上下文检查点不触发委派，也不构成 `participation_delegation` 授权。

## 参与类型

- **当前主 Agent**：负责目的对齐、路由、用户交互、来源去重、冲突呈现和最终综合；
- **额外 Agent**：只处理不重复、可验证、可停止的独立任务，并返回结构化材料；
- **真实参与者**：提供只有本人掌握的价值、权责、承诺、行为意愿或专业责任；
- **用户**：设置参与边界、总上限与授权，保留最终选择权。

## 默认单 Agent

以下情况保持当前主 Agent：

- 目的或当前决定尚未清楚；
- 问题简单、低风险、容易撤回；
- 任务不能拆成互不重复的工作；
- 多个 Agent 只能复述同一框架；
- 需要的是用户价值、真实承诺或现实行为；
- 成本、延迟或隐私负担高于预期增量；
- 宿主能力为 `unknown`、不可用或未授权。

即使用户给了较高上限，也不得为了用满额度而创建 Agent。

## 多 Agent 进入条件

仅当存在至少一个不重复、可验证、可停止的独立任务，并且满足以下至少一种增量价值时建议：

- 不同市场、来源或法规可并行检索；
- 候选解释需要独立形成以降低共享锚定；
- 有必要专门尝试推翻当前候选判断；
- 需要独立审计来源、冲突和遗漏；
- 并行能明显减少大规模研究的等待时间。

额外 Agent 返回：

```text
assigned_question
claims
evidence_and_sources
assumptions
uncertainties
conflicts
what_would_reverse_this
```

每个 Agent 只接收完成其任务所需的最小上下文、数据和能力；不得把完整私有会话复制给所有 Agent。

## 用户设置的边界

用户控制：

```text
协作增强：关闭 / 按需询问 / 在上限内自动
总参与 Agent 上限：包含当前主 Agent
偏好范围：仅本次 / 本会话 / 保存为默认
```

默认建议是 `按需询问`，偏好默认仅本次或本会话。保存为默认必须由用户主动开启，并能够查看、修改和删除。

`在上限内自动` 只表示同一授权范围内不重复询问是否增加 Agent；它不继承公开联网、私有数据、外部行动或新类型任务授权。

## 数量公式

```text
可用额外 Agent 上限 = max(0, 用户总参与上限 - 1)

实际额外 Agent 数 = min(
  独立增量任务数，
  可用额外 Agent 上限，
  产品额外 Agent 安全上限，
  宿主可用额外 Agent 上限，
  成本与延迟预算允许数量
)

实际总参与 Agent 数 = 1 + 实际额外 Agent 数
```

数量表达必须同时显示总数和额外数。额外 Agent 不得递归委派；新的委派需求必须回到主 Agent，重新计入硬上限和本次授权。

## 启用前单屏合同

只在确有增量时展示一次互斥选择，并包含：

- 每个额外 Agent 的具体任务，不用抽象“专家团”代替；
- 当前主 Agent、建议额外 Agent、建议总参与数；
- 用户当前总参与上限与实际计划是否受其限制；
- 使用的数据、按 Agent 裁剪方式与明确排除的数据；
- 公开联网、私有数据、外部行动分别是否允许；
- 模型调用量与可能延迟的相对变化；无法可靠估算时不编造具体价格或时间；
- 任一 Agent 失败后的降级方式；
- 选项：按建议启用、降低数量、保持单 Agent，并允许自由文字进一步收窄任务与数据。

用户提交后形成 `participation_delegation` 授权；展示推荐或默认选中不构成授权。

## 执行与进度

主 Agent 创建不重复任务，并确保计划额外数不超过公式结果。宿主支持进度时，只展示统一任务状态：等待、进行中、完成、失败或已停止。

进度只表示执行状态，不表示证据质量或结论置信度。用户停止未完成工作时，保留已有有效材料，不自动触发任何外部行动。

## 综合纪律

主 Agent 必须：

- 去重同一来源和同一事实链；
- 不按多数票决定；
- 不把模型一致性当现实证据；
- 把分歧定位为事实、预测、价值、约束或风险偏好；
- 把用户价值和底线交还用户；
- 标明采用、舍弃和仍冲突的材料；
- 最终交付一个综合判断和一个主现实证据闭环，而不是观点拼盘。

任何额外 Agent 失败都不应阻塞 B。不得补造失败任务结果，也不得因实际数量少于计划数量而继续声称按原方案完成。

## 协作回执

完成后按 `core/receipts.schema.json` 记录：

- 计划额外数；
- 实际启动、完成和失败数；
- 实际总参与数；
- 每项任务与状态；
- 使用的能力和数据范围；
- 私有数据是否访问；
- 外部行动是否执行；
- 关键分歧、缺失工作和降级。

回执不暴露隐藏思维链。数量、权限或执行状态与计划不一致时必须如实呈现。

## 真人参与路由

以下内容不能由更多 Agent 替代：

- 决策权和预算承诺；
- 受影响者的价值与底线；
- 团队真实权责和执行承诺；
- 客户真实付款或行为意愿；
- 合作方可接受边界与退出条件；
- 持证专业意见和责任。

真人参与最小合同：

```text
为什么需要这位参与者
只请对方回答什么
需要共享哪些最小背景
哪些私有内容不共享
回答如何改变判断
由谁负责发送和收集
```

默认只生成可转发草稿。发送、邀请、建群、预约或联系客户需要独立 `external_action` 授权。真人没有回复或无法参与时，保留缺口并给条件化判断，不冒充对方意愿。

## 授权关系

```text
允许多 Agent
≠ 允许公开联网
≠ 允许读取私有数据
≠ 允许发送、发布或修改外部世界
```

四类授权按 `core/consent.schema.json` 独立记录。B 的反馈、方法选择或当前 Agent 上限均不能扩大其中任何一类授权。

## 执行证明

规范、Schema、线框和 synthetic fixture 只定义 Participation Policy，不自行证明真实 Agent 或真人已经参与。

- 只有实际 delegation trace 与 started / completed / failed receipt 才能证明额外 Agent 的启动和结果；
- 回执中的实际总数必须等于当前主 Agent 加实际启动的额外 Agent；没有额外 Agent 回执时不得声称多 Agent 已发生；
- 真人参与只有真实回复或已授权外部行动的对应回执才能写入事实；可转发草稿不能冒充对方已参与；
- Agent 数量、并行执行或模型一致性本身不证明质量增益，最终判断仍须呈现来源、冲突和现实证据边界。
