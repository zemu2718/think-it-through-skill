# 方法选择

本文件只服务 R-method 的最小推荐。真实目的不足以支撑明确决策问题时先留在 R-align，不展示方法。基本分析始终执行、不可取消、不计入候选数量。可选方法的价值在于改变判断，不是增加框架感。

调研、多 Agent、真人参与、持久化和宿主适配不进入方法注册表；它们分别由 Evidence / Participation Policy 和 Adapter 路由。

## 进入路由前

只有同时满足以下条件才开始：

- 能在不发明动机的前提下暂定说清期望结果；
- 能说清本轮真正需要决定什么；
- 用户不是只在纠正议题或补充目的。

否则按 [交互与表达](interaction-ux.md) 给少量目的方向和同等可见的自由表达入口。文字改题或纠正优先于同时发生的“继续”选择。

## 选择顺序

1. 先判断只做基本分析是否足够。
2. 若有明确倾向、竞争方案、竞争解释或继续/停止冲突，考虑双向钢人。
3. 若当前路径具有可描述的执行过程和明显失败代价，考虑失败预演。
4. 只有仍存在一个未被前述方法覆盖的独特缺口时，才从注册表选择专项卡。
5. 去除重复后，基本分析之外保留 0～3 项；专项方法通常 0～1 项。

## 核心方法路由

| 方法 | 推荐信号 | 不推荐信号 | 独特产出 |
| --- | --- | --- | --- |
| 双向钢人 | 用户已有倾向；A/B 竞争；竞争解释；继续与停止冲突 | 没有真实竞争方向；只是查事实或执行规格 | 两个最强竞争判断的成立条件、机制、证据和代价 |
| 失败预演 | 路径可执行；错误成本明显；准备承诺或已经投入 | 没有候选路径；只需抽象风险定义；紧急危险 | 具体失败结果、关键因果链、早期信号和可控性 |

两种方法可同时推荐，但必须有不同决策价值：双向钢人检验为什么应或不应选择，失败预演检验若这样执行会沿什么机制失败。只能产生同样内容时，保留更能改变判断的一项。

## 专项方法卡路由

从 [方法注册表](methods/registry.yaml) 读取候选卡。只有同时满足以下条件才保留：

- 与当前关键缺口直接匹配；
- 能改变问题重述、变量排序、证据要求或行动边界；
- 不与基本分析、双向钢人或失败预演重复；
- 有明确不适用边界；
- 当前状态和安全条件允许。

多张卡同时匹配时比较独立增量，通常只选一张；没有卡通过时 0 张是正常结果。

## 结构化方法候选

每个用户可见候选都必须规范化为：

```json
{
  "id": "object-calibration",
  "label": "对象校准",
  "description": "分清使用者、付费者和承担代价的人，帮助判断应该先验证谁的需求。",
  "recommended": true
}
```

字段语义：

- `id`：注册表稳定 ID；双向钢人与失败预演分别使用 `two-sided-steelman`、`pre-mortem`；
- `label`：正式方法名，短、平行、同层级；
- `description`：只说明它在当前议题中的独特价值，不复述标签、不引入新目的；
- `recommended`：系统当前是否建议采用，不构成用户确认。

非推荐候选只有与当前议题相关且有独特增量时才可出现，并同样必须有 description。不为丰富界面凑数量。列表外方法仍可由用户自由文字加入，随后重新路由和确认。

普通目的选择、A 答案和 B 反馈不要求 `recommended`；只有 R-method 候选强制完整四字段。

## 用户可见呈现

宿主支持 option description 时，在同一个原生多选项中呈现：

```text
对象校准（推荐）
分清使用者、付费者和承担代价的人，帮助判断应该先验证谁的需求。
```

控件前只保留当前决定、基本分析始终包含、推荐标记说明和操作提示。不得先完整解释一遍，再在控件中只重复名称。

不支持 description 时，按 `label + recommended` 后紧邻 description；没有结构化控件时使用普通编号。降级可以改变版式，不能删除正式名称、推荐状态、当前价值、自由调整或唯一最终组合提交。

方法路由的内部原因、完整目录、来源人物和 ID 不展示给普通用户。确认后只自然回显正式名称。

## R-method 的选择

方法能够组合时，使用原生多选提交最终组合。基本分析始终包含，不作为选项。

- 候选通常 1～3 项；不强制达到普通选项的 2～4 个范围；
- 若只有一个相关候选，可提供“采用该方法 / 仅基本分析”的互斥确认或等价自由表达，不新增无关候选；
- 若 0 个方法有额外价值，自然说明只做基本分析，并取得本轮明确确认；
- 问题正文把当前决定、基本分析说明、操作提示和正式问题分段，正式问题独立位于最后；
- 工具不可用、失败或被拒绝时不重试，立即提供文本等价路径。

产品不创建“其他”或 `Other`。宿主 `Other` 只提供自由输入，不计入候选。选择与文字冲突时以文字为准。

## 调整与组合语义

- 初始推荐只是建议组合，不是已确认组合；
- 原生多选提交后的集合是新的唯一组合；
- “加入 X”保留当前组合并增加 X；
- “取消 X”只移除 X，被取消方法不得换名执行；
- “用 X 替换 Y”才同时移除 Y、增加 X；
- 调整仍在 R-method，每轮最多一个选择问题；
- 最终组合提交后自然回显，例如“好，我们就按刚才选的来：对象校准 + 双向钢人。”

本地方法控件只收集组合，不授权能力调用、委派、私有数据或外部行动。

## 确认判定

构成本轮确认：

- 明确按当前推荐继续；
- 明确只做基本分析；
- 明确加入、取消或替换并形成唯一组合；
- 在控件中提交最终组合；
- 在最初议题中点名方法并明确要求使用。

不构成确认：

- 系统标记 `recommended: true`；
- 默认勾选、打开控件或浏览候选；
- 只补背景、纠正目的；
- “直接判断”“继续说”“你看着办”；
- 历史偏好或过去会话选择；
- 只回应暂定问题模型，没有表达采用哪些角度。

无法确定时留在 R-method。若自由文字改变真实目的，返回 R-align 或重新判断目的充分性。

## 去重与执行检查

进入 A 前确认：

- 最终组合已明确；
- 候选 ID、label 与注册表一致；
- 每项 description 是当前价值，不是通用定义；
- 推荐标记没有被当作确认；
- 每个已确认方法有独特产出；
- 被取消或未确认的方法不会在分析、标题或“顺便考虑”中出现；
- Gate 能力没有被混入方法组合。
